# inflow-worker 重构 · 全局架构方案

> 版本：v1.1（已确认）｜日期：2026-08-23
> 输入：[产品画布 20260823](product-canvas-20260823.md) ｜ [讨论原文](20260823_01_worker重构Skill化产品讨论.md)

---

## 1. 目标与非目标

**目标**

1. 一套面向投产的全局架构：打通「微信 bot → cloud → worker(Skill) → 云端 DB → 前端展示 + 微信推卡」全链路，满足多用户、配额制（10 条/人/天）、7x24 无人值守。
2. worker 重构为 **Skill 化框架**：统一契约下，A 形态（Python 插件，主链路）与 B 形态（Claude 会话，长尾兜底）可互换；新增渠道 = 新增一个自包含 Skill 目录。
3. 现有引擎（inflow_core）已跑通的逻辑细节**保真复用**，不重新趟坑。

**非目标（本期不做）**

- 多 worker 并发调度优化（架构预留扩展位，默认串行）。
- 云端（前端/API/微信接入）**业务逻辑**不动；但 DB schema 新增（skill_usage）、配额接入、新渠道「URL→platform」判定表是**云端配合项**，清单见 §12。
- B 形态 Skill 的全面铺开（仅在 M4 试点 generic 位）。

## 2. 现状盘点：已有资产与真实空白

> 关键发现：讨论中定位的两个卡点（任务下发、进度回传）**已有七成实现**（2026-08-21/22 提交），它们是资产而非空白；真正的空白是这些机制补丁式长在旧引擎上，没有被组织成正式架构。



### 2.1 已投产级的资产（全部继承）


| 资产        | 位置                                                   | 机制要点                                                           |
| --------- | ---------------------------------------------------- | -------------------------------------------------------------- |
| 原子认领 + 租约 | `inflow_worker/claims.py`                            | `FOR UPDATE SKIP LOCKED` 防重复认领；租约 600s 超时可被抢；`claimed_at` 时间戳  |
| 心跳续租      | `runner._heartbeat`                                  | 每 120s 刷新 `claimed_at`；所有权守卫（rowcount=0 即停，不为他人续租）             |
| 重启自回收     | `claims.reclaim_own_host`                            | 按 `hostname-%` 前缀清本机遗留租约，防重启后 job 永久卡死                         |
| CAS 状态机   | `inflow_core/core/pipeline/state_machine.py`         | 合法转换图 + compare-and-set；过期 owner 的写入在 CAS 处失败而非覆盖新 owner       |
| 实时进度      | `ingest_jobs.step_logs`（JSONB）                       | `append_step_log` 独立 session 追加，任意 async 上下文可安全调用              |
| 前端步骤显示    | `pipeline_steps._EXT_RANK`                           | 云端看不到 worker 本地文件，按 status 数值排名判定各步骤 done/active               |
| 断点续跑      | `orchestrator.run_job_resume` + `RETRY_ENTRY_POINTS` | 按已产出文件路径（raw/asr/parsed）跳过已完成阶段                                |
| SFTP 原子传输 | `runner` 四个 SFTP 函数                                  | `.tmp` → rename 原子落盘；120s 超时兜底；permanent/transient 失败分类（3 次熔断） |
| 失败守卫      | `runner.mark_failed_guarded`                         | 终态不覆盖 + 所有权不越权 + 走 transition 保持状态机一致                          |
| 微信推卡队列    | `wechat_callback_queue` 表（云端消费）                      | pending → ready（worker 完成）→ rendering → sent/failed，ilink 发送   |
| 渠道抓取/解析逻辑 | `inflow_core` 13 adapters + 7 templates              | 小宇宙三层降级解析（JSON-LD → `__NEXT_DATA__` → OG）等硬细节                  |
| ASR 子系统   | `parse/audio/*`                                      | 工厂按 `ASR_PROVIDER` 分发 Groq / 听悟 / 本地 whisper；统一落盘三件套           |
| 卡片渲染      | `compose/*` + `prompts/s4`（30 主题）                    | LLM 提字段 → Jinja2 渲染 → Playwright 截 PNG                         |




### 2.2 真实空白（本方案要解决的）

1. **无 Skill 抽象**：加渠道 = 改引擎两处（adapter + template）+ 注册两个 registry；渠道逻辑与通用编排耦合在 orchestrator 巨函数里。
2. **职责无分层**：`runner.py` 混合了调度、传输、capture、状态管理四种职责；`inflow_core` 是 vendor 快照，worker 用不到的云端模块（router/dependencies/user/wechat 模型等）一起背着。
3. **通信参数未契约化**：轮询 10s / 租约 600s / 心跳 120s 散在 settings 里，没有形成云-端共同认可的通信契约文档；长任务（听悟数小时）的进度上报节奏没有约定。
4. **无成本记账**：配额制（10 条/人/天）投产需要每 job 的 ASR/LLM 成本数据，现在没有任何记录。
5. **无监控告警语义**：进度停滞、租约超时、失败率——投产要求的观测点未定义。

## 3. 全局架构



### 3.1 架构总图

```
┌──────────────── 用户侧 ────────────────┐
│                                        │
│   ┌──────────┐         ┌────────────┐  │
│   │ 微信用户   │         │  前端页面    │  │
│   │(微信 bot) │         │ (3~5s轮询)  │  │
│   └────┬─────┘         └─────┬──────┘  │
│        │  ① ilink 收发        │  ② 轮询   │
└────────│─────────────────────│─────────┘
         │                     │
         ▼                     ▼
┌─────────────────────────────────────────┐
│  CLOUD（腾讯云，仅交互与展示）              │
│  · 微信 bot 接入：收消息 → 落盘/登记 job   │
│  · 前端 API：读 status + step_logs        │
│  · callback_loop：job=ready → 渲染 → 推卡 │
└───────┬─────────────────────────┬────────┘
   PostgreSQL（唯一命令/状态/结果）   SFTP（唯一大文件通道）
   │  ③ 任务认领 / 进度 / 结果     │  ④ 素材下行 / 卡片上行
   │                            │
   ▼                            ▼
┌─────────────────────────────────────────┐
│  WORKER（本地 Windows 7x24，只出站连接）   │
│  scheduler → runtime(executor 通用编排)   │
│    → skills(_shared + 渠道钩子)           │
│  transport(SFTP)                        │
└─────────────────────────────────────────┘
```

**读图要点**：微信用户与前端页面都只在「用户侧」，各自只连 CLOUD；WORKER 只连 CLOUD 的 PostgreSQL 与 SFTP，**worker 与微信用户之间没有任何直连**。worker 处理完 → job 到 ready → CLOUD 的 callback_loop 消费 `wechat_callback_queue` → ilink 推卡给用户（链路 ⑤）。



### 3.2 五条链路（谁写什么、谁读什么）


| #   | 链路    | 方向                  | 通道         | 机制                                                                                            |
| --- | ----- | ------------------- | ---------- | --------------------------------------------------------------------------------------------- |
| 1   | 任务下发  | cloud → worker      | PostgreSQL | cloud 写 `ingest_jobs`（external_processing=true, status=pending）；worker 轮询认领（SKIP LOCKED + 租约） |
| 2   | 进度回传  | worker → 前端         | PostgreSQL | worker 写 `status`（CAS transition）+ `step_logs`（JSONB 追加）；前端 3~5s 轮询                           |
| 3   | 素材下行  | cloud → worker      | SFTP       | cloud 收件落盘 `00_staging/` + 登记 `staging_file_path`；worker 拉取后完成 capture                        |
| 4   | 资产上行  | worker → cloud      | SFTP       | PNG（必需，失败即 failed）+ HTML（best-effort）原子落盘 `03_display/`                                       |
| 5   | 结果与推卡 | worker → cloud → 微信 | PostgreSQL | worker 写 `articles`/路径字段；job 到 ready 后云端 callback_loop 渲染推卡                                   |


**架构不变式**：DB 是唯一命令通道，SFTP 是唯一大文件通道。worker 永远只出站连接，不需要固定 IP / 公网入站——NAT 约束天然满足。

## 4. 通信契约（投产参数，云-端共同遵守）



### 4.1 调度参数


| 参数                         | 值                    | 语义                                                    |
| -------------------------- | -------------------- | ----------------------------------------------------- |
| `SCAN_INTERVAL_S`          | 10（空闲）/ 2（刚处理完一单后首扫） | worker 轮询间隔；用户感知「最坏 10s 开工」                           |
| `LEASE_SECONDS`            | 600                  | 租约超时；崩溃 worker 的 job 10 分钟后可被抢                        |
| `HEARTBEAT_INTERVAL_S`     | 120                  | 心跳刷新 `claimed_at`；满足「几秒~十几秒知道没死」由 step_logs 承担，心跳只管租约 |
| `STAGING_PULL_MAX_RETRIES` | 3                    | 瞬时失败熔断阈值                                              |




### 4.2 进度上报节奏（Skill 必须遵守）

1. **每个状态机阶段开始/结束**：必报一条 step_log（谁在跑、跑到哪）。
2. **长任务周期 detail**：单阶段 > 120s（ASR 下载/转录）时，每 60s 追加一条 detail（字节数/时间戳/等待原因）——这是「知道它没死」的来源。
3. **失败**：阶段 + 原因截断 500 字，走 `mark_failed_guarded` 语义（终态不覆盖、所有权不越权）。



### 4.3 僵死与故障语义


| 故障          | 判定                          | 自愈                                             |
| ----------- | --------------------------- | ---------------------------------------------- |
| worker 进程崩溃 | `claimed_at` 超过 600s 未刷新    | 其他/本机 worker 重新认领，断点续跑                         |
| worker 整机重启 | `reclaim_own_host` 前缀匹配     | 启动时清本机遗留租约                                     |
| 长任务假死       | step_logs 停滞 > 10min（云端观测点） | 云端告警（M3）；worker 侧阶段内超时上限（ASR 单文件上限、LLM 重试上限）兜底 |
| 云端 DB 不可达   | 认领异常                        | 退避重试（现有日志语义保留）                                 |

### 4.4 启动连通性自检（M1 起，投产前提的即时验证）

worker 启动时探测三条外部依赖并写日志 + 告警：**Groq API 可达性 / 云端 PG / 云端 SFTP**。任一失败 → 明确日志告警（不阻塞启动，进入轮询自愈，但状态可观测）。这是「家用 WiFi 能否出海访问 Groq」「PG 白名单是否放行」等投产前提的**当场验证**，不留到 M3。

## 5. Skill 框架设计



### 5.1 统一契约（A/B 同构的核心）

```python
# framework/runtime/skill.py

class SkillContext:
    """框架注入：Skill 只能用这些受控口，不直接碰全局。"""
    job: JobContext            # job_id / user_id / source_url / staging 路径 / 已产出文件路径
    settings: WorkerSettings
    report: ProgressReporter   # report.stage(name) / report.detail(msg) → CAS + step_logs
    advance: StatusTransition  # advance("transcribing") → 状态机 CAS 前进
    storage: Storage           # read_staging() / write_raw() / write_parsed() / card 资产
    sftp: Transport            # 拉暂存 / 回传资产（失败语义内置）
    llm: LLMClient             # 固定 prompt 调用 + usage 返回（成本记账数据源）
    logger: Logger

class SkillResult:
    status: Literal["ready", "failed"]
    error_stage: str | None
    assets: dict[str, str]     # raw/asr/parsed/png 路径（写回 ingest_jobs 对应列）

class SkillContract(Protocol):
    id: str                            # "xiaoyuzhou"
    version: str                       # "1.2.0" —— Skill 升级审计
    triggers: TriggerSpec              # 路由声明（见 5.2）
    content_type: Literal["audio", "article"]   # 决定 executor 走 transcribe 还是 normalize 分支
    async def execute(self, ctx: SkillContext) -> SkillResult: ...
```

**关键约束**

- Skill **不直接开 DB session**、不直接改 `claimed_at`、不直接写 status——全部经 ctx（心跳、CAS、守卫在框架层一次实现，所有 Skill 免费获得崩溃安全）。
- `ingest_jobs.status` 状态机是**云-端契约，一字不改**（云端前端 `_EXT_RANK` 在消费它）；断点续跑与内容类型路由由 **executor 通用编排**承担（`run_job_resume` 平移，平台无关），skill 不声明状态机节点，`advance()` 仍在框架层做合法性校验。
- LLM 调用必经 `ctx.llm`（记录 token usage → 成本记账），ASR 经 `_shared/asr`（统一三件套落盘）。



### 5.2 路由：job → Skill

```
云端接单：按 URL 域名判定 source_platform（现有逻辑，云端职责，不变）
worker 路由：skill_id = TRIGGER_TABLE[source_platform]  → 无命中 → generic
```

- 一期**不加新列**，直接用现有 `source_platform`（wechat/xiaoyuzhou/upload/paste/...）推导，零 DB 变更。
- TriggerSpec 声明式注册：`platform="xiaoyuzhou"`、`capture_method="paste"` 等；注册表启动时构建，冲突检测（两个 skill 声明同一 platform → 启动失败）。
- 兜底规则：`generic` skill 永远存在，任何路由不中的 job 都有归宿（现状语义保持）。



### 5.3 执行生命周期（框架 executor）

```
认领 job（scheduler）
  → 路由 skill（registry：trigger → skill）
  → 校验 skill.content_type 与 article.content_type 一致
  → 构建 SkillContext（起心跳 task）
  → executor 通用编排（run_job_resume 平移，按 job.status 断点续跑）：
      · capture → skill.capture_fn（平台抓取 / staging 拉取）
      · 分支   → executor 按 content_type 路由（audio→transcribe，article→normalize）
      · parse  → skill.parse_fn（平台模板 + prompt）
      · compose → _shared/render；on_composed 回传 PNG
      · index  → executor
  → 成功 → 资产路径写回 → 状态到 ready → 云端推卡队列自动接手
     失败 → mark_failed_guarded（终态/所有权守卫）
  → finally：停心跳 → release_lease
```



### 5.4 A / B 双形态


|     | A：Python 插件（一期主力）                    | B：Claude 会话（M4 试点）                                                       |
| --- | ------------------------------------ | ------------------------------------------------------------------------ |
| 载体  | `framework/skills/<name>/skill.py` 实现 contract | `framework/skills/<name>/SKILL.md` 指令包 + `claude_runner.py` 适配器                    |
| 执行  | 进程内直接调用                              | 子进程 `claude -p --output-format stream-json`，适配器把流事件翻译成 `report.detail()` |
| 权限  | 正常 Python                            | 受限：只读 staging、只写指定目录、DB 经受限 CLI，max-turns 成本上限                           |
| 适用  | 高频确定性渠道（小宇宙/公众号/upload）              | generic 兜底、新渠道试水（B 是 A 的孵化器）                                             |


B 适配器实现**同一个 SkillContract**——调度器无感知，这是「可互换」的落点。

## 10. 部署要求与风险

**部署形态（已定）**：cloud = 腾讯云；worker = **本地 Windows 家用机（7x24 开机）**。

**通信通道（已定：公网直连）**：worker 直连云端 PG(5432) 与 SFTP(22)，不做隧道。
- 家用宽带为动态公网 IP——云端按 IP 放行时，IP 变更会导致 worker 失联，靠现有「退避重试 + 断线自愈 + 日志告警」兜底；M3 观测告警兜住「长时间失联无人知」。
- 若 IP 变更过于频繁影响投产，可平滑切换出站隧道（Tailscale/WireGuard）——架构不变式（只出站）天然兼容，切换不动业务代码。

**worker 机器硬要求（Windows）**：
- 可出海访问 Groq——家用 WiFi 需保证；M1 连通性自检当场验证（失败即告警）
- 云端 PG 5432 + SFTP 22 放行本机家庭公网 IP（动态 IP 变更处理见上）
- SFTP 账号对 `00_staging` 可读、`03_display` 可写
- Python 3.11+ / Playwright chromium（Windows 原生支持）
- 开机自启 + 崩溃重启：NSSM/WinSW 注册为 Windows 服务（替代 launchd/systemd）


| 风险                            | 等级  | 缓解                                     |
| ----------------------------- | --- | -------------------------------------- |
| 微信 bot 侧（ilink）封禁/限流          | 高   | 云端职责，与本次重构解耦；建议云端做发送退避与账号备份（M3 提醒云端）   |
| 免费额度成本失衡（ASR+LLM 全在 worker 侧） | 高   | M3 记账先行，投产前算清单均成本再定额度                  |
| 单 worker 串行吞吐上限（转录任务挤占队列）     | 中   | loop 预留并发度配置；SKIP LOCKED 天然支持多实例，随时横向扩 |
| 7x24 机器（已定：Windows+家用WiFi+公网直连）                   | 中   | M1/M2 本机开发；M3 前验证家用WiFi可出海访问 Groq + Windows 服务开机自启；公网直连下动态 IP 变更靠退避自愈 + M3 告警兜底，频繁可平滑切出站隧道         |
| 迁移期双轨混乱                       | 低   | M1 双轨共存但只有框架接认领；M2 删引擎即断舍离             |
