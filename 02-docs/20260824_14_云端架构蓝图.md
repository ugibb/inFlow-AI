# Cloud 端架构蓝图

> 生成于 2026-08-24，基于 Cloud 端代码静态分析（详见 [20260824_13_云端后端代码分析报告](./20260824_13_云端后端代码分析报告.md)）与产品讨论结论。
> 本文是「重构后的 Cloud 端应该长成什么样」的权威参照，也是后续所有迭代的骨架。

---

## 1. 背景与重构目标

### 1.1 现状问题

Cloud 端（本仓库 `ugibb/inFlow-AI`）经过多轮演进，代码结构与实际定位严重脱节：


| 问题              | 表现                                                                                                                                                 |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **引擎双头共用**      | `03-src/core` 15,366 行同时服务「云端 server」与「本地 worker」，但 worker 已于 2026-08 独立重构（新架构 `framework/skills`，零依赖本仓库），留下 8,000+ 行「server 用不到、删了又怕 worker 崩」的死肉 |
| **运行时边界不可见**    | `parse/`、`audio/` 转写、`pipeline/steps.py` 等模块 server 只在 legacy 路径（`_run_regenerate_ai` 等）引用，external 模式下实际不执行——「哪套代码在跑」靠猜                           |
| **断线功能**        | 学习路径 `routers/learning.py`、周期回顾 `extensions/review/` 前端已接线但后端未挂载 → 线上 404                                                                          |
| **死代码堆积**       | 前端 `ChangePasswordModal`、api.ts 10 个死函数；后端 `obsidian/writer.py`、`review_cron_loop`、core 的 `publish/`、`events.py`、`card_toolbar_injector.py` 等      |
| **外部协同能力无统一管理** | wechat-bot 独立进程、obsidian 同步等「需外部协同的能力」散在 extensions/，启停靠脚本手动，状态不可见，扩展新 bot（如飞书）无模板                                                                 |
| **文档失实**        | README 仍写着「worker 经 pip git 依赖 core」，已不符合事实                                                                                                        |




### 1.2 重构目标

1. **以前端功能为蓝本**：前端 13 页面、12+ 功能面全部保留；跑不通的功能（学习路径、周期回顾）**保留现状，不修不动**，后期有需要再优化扩展
2. **运行时边界清晰**：Cloud 仓库只装「Cloud 运行时在跑的代码」，让「哪套在跑」一眼可见
3. **结构合理、方便扩展**：新功能、新内容类型、新 AI 模型、新外部协同插件（bot 等）都能在不推翻架构的前提下接入
4. **外部协同能力插件化**：wechat / obsidian（及未来飞书 bot 等）以**插件**形态存在，提供统一的状态展示与启停管理，前端可操作
5. **无需考虑 worker，不留一手**：worker 已完全独立，本仓库代码只需对 Cloud 运行时负责



### 1.3 边界原则（一句话）

> **Cloud 仓库 = 前端功能 + 为前端服务的后端 API + 收件登记 + 插件化的外部协同能力。凡是前端不触发、且不属于收件登记、也不属于插件的能力，一律不留在本仓库。**

## 2. 架构原则


| 原则               | 含义                                                            |
| ---------------- | ------------------------------------------------------------- |
| **进程边界 > 目录边界**  | 每个独立进程（backend / 插件进程 / infra 容器 / worker）职责单一，生命周期互不耦合       |
| **backend 即控制面** | 所有对外功能与插件启停都以 backend 为唯一入口；脚本只负责拉起 backend 与 infra           |
| **main.py 即真相源** | 后端对外功能 = `main.py` 里挂载的 router 清单 + 插件注册表。挂载/启用 = 上线，未启用 = 明示 |
| **薄接入 + 厚引擎**    | routers 只做 HTTP 语义与参数校验；业务逻辑进 core 领域模块；跨域逻辑进 services        |
| **异步只登记**        | 一切重计算走 `IngestJob` 登记 → 外部 worker 认领。server 不持有任何重计算能力        |
| **扩展点显式化**       | 平台识别 / AI 模型 / 新功能面 / 新插件都有明确入口，新增不破坏既有代码                     |
| **唯一数据源**        | PostgreSQL 是唯一持久层，backend / 插件进程 / worker 均直接读写，不引入缓存一致性黑盒    |

## 3. 目标运行时拓扑

```
┌────────────────────────────── Cloud 主机（生产：宝塔 /www/wwwroot/inflow-ai）──────────────────────────────┐
│                                                                                                        │
│  docker compose（infra 容器，start-server.sh 管理）                                                       │
│  ├─ postgres:5432     ← 唯一数据源（backend / 插件进程 / 远程 worker 直连）                                 │
│  ├─ redis             ← 缓存 / 轻量队列（当前未重度使用，保留占位）                                        │
│  ├─ nginx:80/443      ← 反代 frontend 静态 + backend /api 同源                                          │
│  └─ frontend          ← Next.js standalone，静态托管                                                    │
│                                                                                                        │
│  宿主机直跑进程（start-server.sh 管理，PID 落 .server/）                                                  │
│  └─ backend:8000      ← FastAPI 单包 backend（唯一 HTTP API 面，lifespan 只 init_db）                     │
│                        ├─ 路由前缀：/api/articles knowledge system assistant auth users ingest           │
│                        │           /api/wechat research sync images health                               │
│                        ├─ 插件管理：/api/plugins（状态 + 启停）                                            │
│                        └─ PluginManager 拉起/监督的插件子进程                                              │
│                             ├─ wechat-bot（进程型插件，微信长轮询，HTTP 回访 backend）                      │
│                             └─ feishu-bot（未来，进程型插件）                                              │
│                                                                                                        │
└────────────────────────────────────────────────────────────────────────────────────────────────────────┘
        ▲                                                        ▲
        │ 浏览器访问（frontend 同源 /api，nginx 反代）             │ 仅安全组白名单放行
        ▼                                                        ▼
   用户浏览器                                        ┌──────────────────────────┐
                                                   │ 本地 worker（独立仓库）    │
                                                   │ ugibb/inflow-worker        │
                                                   │ framework/skills 新架构    │
                                                   │ 轮询认领 IngestJob         │
                                                   │ SFTP 回传产物，写回 PG      │
                                                   └──────────────────────────┘
```

**要点**：

- **backend 是唯一控制面**——所有浏览器请求、插件启停、插件回调都走它；插件进程（wechat-bot 等）由 backend 的 `PluginManager` 拉起与监督，不再由脚本单拉
- **backend 自身保持零后台任务**——init_db 之外，重任务一律外置（worker / 插件进程）
- **worker 是外部消费者**——只通过 PG 认领任务、SFTP 回传，不碰本仓库代码

## 4. 后端代码架构



### 4.1 分层与职责

```
backend/                # 单一 Python 包 = 原 server/ + core/ 合并
├── main.py              # 唯一装配点：中间件 + lifespan(init_db + 插件初始化) + router 挂载
├── routers/             # 接入层：薄路由，参数校验 + 转发 service/core
├── services/            # 服务层（可选，按需）：跨 router 复用的业务编排
├── plugins/             # 插件体系：可启停的外部协同能力（见 4.3）
└── core/                # 引擎层：被 routers/services 直接 import 的领域模块（收敛后 ~4,000 行）
```


| 层                 | 职责                                             | 规则                                                 |
| ----------------- | ---------------------------------------------- | -------------------------------------------------- |
| **接入层 routers/**  | HTTP 语义（状态码、分页、鉴权依赖注入）、参数校验、错误翻译               | 不含业务逻辑；一个功能面一个 router 文件                           |
| **服务层 services/** | 跨 router 复用的编排（如「推送某文章到微信」被多处调用）               | 只在确有跨域复用时创建，不为单点逻辑造层                               |
| **插件体系 plugins/** | 需要外部协同、有启停语义的能力（wechat / obsidian / 未来 feishu） | 统一 Plugin 基类 + PluginManager；进程型插件与 backend 生命周期解耦 |
| **引擎 core/**      | 数据模型、迁移、LLM/embedding、存储抽象、ingest 收件           | 只保留 server 运行时在用的部分（见第 5 章）                        |


> `research/`（SSE 研究）不是插件——它在 backend 内、无独立进程、无启停语义，是普通能力面。



### 4.2 挂载即真相源

`main.py` 的 router 注册表就是「Cloud 对外功能清单」。未启用的功能**不混在已启用区**，移入 `_pending/` 并显式标注：

```
routers/
├── articles.py      # ✅ /api/articles      前端：采集、文章管理、阅读
├── knowledge.py     # ✅ /api/knowledge     前端：标签、文件夹、图谱、思维导图、统计
├── assistant.py     # ✅ /api/assistant     前端：RAG 问答
├── auth.py          # ✅ /api/auth          前端：登录
├── users.py         # ✅ /api/users         前端：用户管理（超管）
├── system.py        # ✅ /api/system        前端：系统运维（超管）
├── research.py      # ✅ /api/research      前端：SSE 深度研究（原 extensions/research 归位，非插件）
├── _pending/        # ⚠️ 未启用区（保留现状，不修不挂）
│   ├── learning.py  #     /api/paths        学习路径（前端已接线，后端 404，暂留）
│   └── review.py    #     /api/review       周期回顾（同）
```

插件提供的路由**不在这里**，由插件自身声明、`PluginManager` 挂载（见 4.3/4.4）。

### 4.3 插件体系（外部协同能力）



#### 4.3.1 为什么插件化

wechat / obsidian（及未来飞书 bot 等）的共同点，决定它们不能当普通页面功能看待：


| 特征              | 说明                                     |
| --------------- | -------------------------------------- |
| **需要外部协同**      | 依赖第三方服务：微信/iLink 通道、Obsidian 插件、飞书开放平台 |
| **有独立运行时或独立契约** | 进程型插件是常驻长轮询进程；API 型插件对外部插件提供同步契约       |
| **需要启停管理**      | 服务会挂、会要升级、会要停用——需要运维视角的状态展示与启停操作       |
| **可扩展**         | 未来加「飞书 bot」应是新增一个插件，而非改现有代码            |




#### 4.3.2 插件分类


| 类型             | 运行时                      | 启停语义                                        | 示例                |
| -------------- | ------------------------ | ------------------------------------------- | ----------------- |
| **进程型（bot 类）** | 独立子进程，由 PluginManager 拉起 | `start/stop` = 拉起 / 杀掉子进程（subprocess + PID） | wechat、feishu（未来） |
| **API 型（同步类）** | backend 内路由，对外部插件提供 API  | `enabled/disabled` = 路由功能开关                 | obsidian          |




#### 4.3.3 插件目录结构

> **一个插件 = `plugins/<id>/` 下一个自包含目录**：声明（plugin.py）+ 对外路由（router.py）+ 可选进程入口（bot.py），自带版本与配置声明。新增插件 = 新增一个目录 + 注册一行，不触碰既有插件。

```
backend/plugins/
├── __init__.py        # 导出 PluginManager 单例
├── base.py            # Plugin 基类 + PluginStatus/PluginInfo 模型
├── registry.py        # 内置插件注册表（代码内声明：wechat / obsidian）
├── manager.py         # PluginManager：状态聚合、启停调度、进程监督
├── process.py         # 子进程管理（subprocess + PID 落 .server/plugins/{id}.pid）
├── status.py          # 状态判定（进程存活 / 心跳 / 配置就绪）
├── router.py          # GET/POST /api/plugins/*（见 4.4）
├── wechat/
│   ├── plugin.py      # Plugin 声明（id/name/kind/auto_start/required_config/routers/start/stop）
│   ├── router.py      # /api/wechat/*（绑定、状态、账号）
│   └── bot.py         # 进程入口（python -m backend.plugins.wechat.bot）
├── obsidian/
│   ├── plugin.py      # Plugin 声明（API 型）
│   └── router.py      # /api/sync/*
└── feishu/            # （未来）进程型插件，模板同上
```



#### 4.3.4 Plugin 基类契约

```python
class Plugin(ABC):
    id: str                 # 唯一 id，如 "wechat"
    name: str               # 展示名
    description: str
    version: str
    kind: "process" | "api"
    auto_start: bool        # backend 启动时是否自动拉起
    required_config: list   # 需要的配置 key（config_store），未配齐 → not_configured

    def routers(self) -> list[APIRouter]: ...   # 插件提供的 API 路由
    def status(self) -> PluginStatus: ...       # running/stopped/error/not_configured
    async def start(self): ...                  # 进程型: process.py 拉起; API 型: 置 enabled
    async def stop(self): ...                   # 进程型: 杀进程; API 型: 置 disabled
    async def health(self) -> dict: ...         # 心跳/最后活跃/错误详情
```

**状态机**：`not_configured → stopped ⇄ running → error`

**状态来源**：

- 进程型：子进程存活 + PID 文件 + 心跳（如 wechat_accounts 表心跳字段 / 最后活跃时间）
- API 型：配置就绪 + 功能开关



#### 4.3.5 PluginManager

- **注册表**：内置插件在 `registry.py` 声明，backend 启动时加载
- **状态聚合**：为前端提供全插件状态快照
- **启停调度**：`start/stop/restart` 收敛到 manager，进程型经 `process.py`，API 型改开关
- **进程监督**：记录 PID；backend 退出时（`stop-server.sh`）优雅停止全部运行中插件
- **自动恢复**：`auto_start=true` 的插件在 backend 启动时自动拉起



#### 4.3.6 插件管理 API（新增）

```
GET  /api/plugins                          # 全插件列表 + 状态（含配置就绪 / 进程存活 / 心跳）
POST /api/plugins/{id}/start               # 启动
POST /api/plugins/{id}/stop                # 停止
POST /api/plugins/{id}/restart             # 重启
```

响应示例：

```json
[
  {
    "id": "wechat", "name": "微信 Bot", "kind": "process",
    "status": "running", "version": "1.0.0",
    "config_ready": true, "auto_start": true,
    "health": { "heartbeat_at": "2026-08-24T10:00:00Z", "accounts": 3 }
  },
  {
    "id": "obsidian", "name": "Obsidian 同步", "kind": "api",
    "status": "enabled", "config_ready": true,
    "health": { "synced_articles": 128 }
  }
]
```



#### 4.3.7 前端插件管理页（新增功能）

- **定位**：这是本次重构**唯一新增的前端功能**（蓝本的显式例外，用户拍板）
- **入口**：`/settings` 下「插件管理」Tab，或独立 `/plugins` 页（均需超管权限）
- **每插件一张卡**：

```
┌─ 微信 Bot ──────────────────────────────────────┐
│  进程型 · v1.0.0           ● 运行中             │
│  长轮询接收微信收藏与 /r /a /c 命令，推送精华卡     │
│  配置就绪 ✓ · 自动启动 ✓ · 活跃账号 3            │
│  [ 停止 ]  [ 重启 ]                              │
└─────────────────────────────────────────────────┘
```

- 状态徽章配色：`running` 绿 / `stopped` 灰 / `error` 红 / `not_configured` 橙
- 操作后轮询 `/api/plugins` 刷新状态；异常状态提示错误详情



### 4.4 插件与 start-server.sh 的启停边界


| 组件                                      | 谁负责拉起                                   | 谁负责停止                                        | 说明                                   |
| --------------------------------------- | --------------------------------------- | -------------------------------------------- | ------------------------------------ |
| infra 容器（postgres/redis/nginx/frontend） | `start-server.sh`                       | `stop-server.sh`（容器保留）                       | 基础设施，不经插件系统                          |
| backend                                 | `start-server.sh`                       | `stop-server.sh`                             | 唯一控制面                                |
| 进程型插件（wechat-bot 等）                     | **backend PluginManager**（按 auto_start） | **backend PluginManager**（/api/plugins stop） | 前端可操作；stop-server.sh 通知 backend 优雅停止 |


> 兜底：调试时仍可用 `python -m backend.plugins.wechat.bot` 手动拉起单个插件进程，但不作为常态管理路径。

## 6. 数据层



### 6.1 核心实体


| 实体       | 表                     | 说明                                               |
| -------- | --------------------- | ------------------------------------------------ |
| 用户       | users                 | 角色（超管/普通）、状态、sync token 版本                       |
| 文章       | articles              | 正文/摘要/元数据/embedding 向量/pipeline 阶段               |
| 标签       | tags                  | 文章标签，支持合并/批量删除                                   |
| 文件夹      | folders               | 文章归档组织                                           |
| 知识关系     | knowledge_edges       | 图谱边（LLM 生成）                                      |
| 采集任务     | ingest_jobs           | **异步登记核心**：worker 认领、步骤状态、step_logs              |
| 微信账号     | wechat_accounts       | 绑定账号 + bot 心跳                                    |
| 回调队列     | wechat_callback_queue | 卡片推送回调                                           |
| 回顾计划     | review_schedules      | 周期回顾（未启用，保留）                                     |
| 插件状态（新增） | plugin_states         | 插件启停状态 / auto_start / 最后心跳（进程型状态可由此持久化，避免只靠进程探测） |




### 6.2 迁移策略

- 所有 schema 变更走 `backend/core/migrations/*.sql`，命名递增编号
- `backend` 启动 `init_db()` 时自动执行缺失迁移（幂等）
- **约束**：迁移只能新增/变更，不删除历史编号；删除字段用 `ALTER TABLE ... DROP` 而非重写历史

## 7. 扩展点设计（方便后期扩展）

这是「方便后期扩展」的落地。Cloud 端扩展一律通过以下六个显式入口，**不破坏既有结构**：

### 7.1 新增前端功能面

1. 前端加页面（组件/路由/api.ts 函数）
2. 后端：`routers/` 新增一个 router 文件，`main.py` 挂载即上线
3. 引擎能力复用 `backend/core/` 既有领域模块，不新造轮子

> 示例：未来加「收藏夹共享」→ 新增 `routers/collections.py` + core 里一个 collections 领域模块。



### 7.2 新增内容类型 / 平台（收件）

- Cloud：`backend/core/ingest/adapters/registry.py` 加一条平台识别条目（只需 `can_handle` + 平台信息）
- Worker：对应 skill 实现采集/解析（worker 仓库）
- **Server 零改动**——收件仍走 `/api/ingest` 登记，worker 认领

> 示例：未来加「豆瓣读书」→ registry 加 douban.py（10 行识别逻辑）+ worker 加 douban skill。



### 7.3 新增 AI 模型 / 服务商

- 统一走 `backend/core/shared/ai_service.py` 出口 + `config_manager` 配置 + settings 页「测试连接」
- 模型切换不触碰任何 router / 业务代码

> 示例：换 LLM → 改 `config_store.json` 对应 group，settings 页测试通过即生效。



### 7.4 新增异步重任务

- 建一种 IngestJob 类型（`ingest_jobs` 表 + orchestrator 登记分支）
- worker 侧新增认领逻辑
- Cloud 只负责登记 + 展示进度，不持有计算能力

> 示例：未来加「视频字幕批量清洗」→ 新 job type + worker 新 skill。



### 7.5 新增外部协同插件（bot 等）★ 插件化扩展

1. 在 `backend/plugins/` 建一个目录（如 `feishu/`）：`plugin.py`（声明 id/kind/auto_start/routers/start/stop）+ 路由 + 进程入口
2. `backend/plugins/registry.py` 注册一行
3. `PluginManager` 自动加载：状态出现在 `/api/plugins`，前端插件管理页**自动出现**该插件的卡片（启停无需改前端代码）
4. 进程型插件复刻 `wechat/` 模板（process.py 负责拉起/监督）

> 示例：未来加「飞书 Bot」→ 复制 wechat 模板为 feishu/，改外部 API 调用即可，一条注册，前端零改动。



### 7.6 新增进程型能力的通用路径

- 若新能力**不需要**外部 bot 语义（如本地定时任务），优先走 7.4（IngestJob 异步任务）或 services；**只有**需要外部协同 + 启停管理时才走 7.5 插件化
