# 微信小程序「微信登录」方案（替换账号密码登录）

> 日期：2026-09-05 · 状态：**已确认，实施中**（决策：免邀请码先行，体验成员白名单做门禁） · 关联：`20260905_微信小程序MVP方案.md`

## 1. 现状与问题

- 小程序端目前只有账号密码登录（`POST /api/auth/login`），首次要输、token 30 天过期后又要输——移动端体验差。
- 微信小程序标准做法：`wx.login()` 拿临时 code → 后端 `code2session` 换 `openid` → 绑定用户发 JWT。

## 2. 关键约束（决定方案形态）

| 事实 | 影响 |
|---|---|
| `articles` 表按 `user_id` 隔离（`uq_articles_user_url`） | 微信登录**不能新建空账号**——会看到一个空库；必须绑定到既有账号（库的主人） |
| 个人主体小程序，不上架、自己 + 少数朋友使用 | 无需企业级多租户；一个「绑定目标账号」+ 邀请码足够 |
| `wx.getUserProfile` 已对新小程序回收（静默获取只返回灰头像+「微信用户」） | 昵称头像改用官方「**头像昵称填写能力**」：用户在首次登录页**主动**选头像（微信头像/相册/拍照）+ 填昵称（键盘带微信昵称快捷填充），存入绑定记录——这是平台回收静默获取后的官方替代路径 |
| JWT 签发/校验、`create_access_token` 现成 | 后端只加一个端点 + 一张绑定表，零侵入 |

## 3. 方案选型

| 方案 | 首次访问 | 后续访问 | 评价 |
|---|---|---|---|
| A. 首次输一次账号密码绑定 | 输账号+密码（仅一次） | 全自动 | 安全但「还是要账号密码」，不解决痛点 |
| B. 邀请码绑定指定账号 | 输一次 6 位邀请码 | 全自动 | 无需知道账号密码；**公开上架时用**，改 `.env` 即可换码/关闭 |
| **C. openid 直登（无校验）——体验版阶段默认** | 全自动 | 全自动 | 靠体验成员白名单做门禁（约 15 人上限），首次访问零输入 |

**邀请码不是合规要求**（微信从未要求，上架审核时反而可能因「审核员进不去」被驳回），**也不是普遍必要的安全措施**，而是「内容访问门禁」开关，按分发形态取用：

- **体验版分发（当前阶段，默认）→ 选 C（免验直进）**：体验版本身有官方门禁——只有 mp 后台手动添加的「体验成员」（个人主体约 15 人上限）能打开小程序，陌生人连入口都没有。邀请码留空，首次访问**零输入全自动**进库。
- **将来上架公开分发 → 切到 B**：任何微信用户都能搜到打开，此时必须设邀请码（或换别的门禁），防止陌生人绑进账号看整库。`.env` 设上码重启即生效，无需改代码。

## 4. 交互时序

### 首次访问（默认：邀请码留空，全自动）
```
用户打开小程序
  → app.onLaunch：本地无 token
  → wx.login() 取 code
  → POST /api/auth/wechat {code, nickname?, avatar_base64?}
  ← 200 {access_token, user, wx_profile}   # openid 自动绑定到目标账号
  → reLaunch 首页，全程无任何输入
```

### 首次访问（设了邀请码时，上架公开分发形态）
```
用户打开小程序
  → app.onLaunch：本地无 token
  → wx.login() 取 code
  → POST /api/auth/wechat {code}
  ← 403 {detail: "invite_required"}        # 后端要求邀请码
  → 跳登录页：头像选择 + 昵称输入（均选填，微信键盘快捷填充昵称）+ 邀请码 + 「微信一键登录」
  → wx.login() 取新 code（code 一次性）
  → POST /api/auth/wechat {code, invite_code, nickname?, avatar_base64?}
  ← 200 {access_token, user}               # openid 已绑定到目标账号
  → reLaunch 首页，此后永久免登录
```

### 后续每次访问（无感）
```
app.onLaunch：本地 token 缺失/过期
  → wx.login() → POST /api/auth/wechat {code}
  ← 200 {access_token, user}               # openid 已在绑定表
  → 直接进首页，用户全程无感知
```

本地 token 仍有效时（30 天内）沿用，不每次打扰微信接口——即最多每 30 天走一次静默换发。

## 5. 后端改动（FastAPI）

### 5.1 新表 `wechat_bindings`（**不改 `users` 表**；新建表由启动时 `create_all` 自动建，无需手工迁移）

```python
# backend/core/models/wechat_binding.py
class WechatBinding(Base):
    __tablename__ = 'wechat_bindings'
    id          = Column(UUID, primary_key=True, default=uuid.uuid4)
    user_id     = Column(UUID(as_uuid=True), ForeignKey('users.id', ondelete='CASCADE'), nullable=False, index=True)
    openid      = Column(String(64), unique=True, nullable=False, index=True)  # 一个微信绑一个账号；多人=多行同 user_id
    nickname    = Column(String(64), nullable=True)    # 用户主动填写的昵称（填写能力，非抓取）
    avatar      = Column(Text, nullable=True)          # 头像 data URI（用户主动选择后上传，≤1MB）
    created_at  = Column(DateTime(timezone=True), server_default=func.now())
```

- **`users` 表零字段改动**（现表没有 openid 字段也不需要加）：绑定关系独立成表，不动任何存量表。
- 为什么不往 `users` 加 openid 列：① 改存量列要手工 `ALTER`；② 单列只能绑一个微信，朋友共享账号需 1:N；③ Web 端账号体系零影响。
- 建表遵循项目双轨约定：ORM 声明（`init_db()` 的 `create_all` 自动建新表）+ `core/migrations/023_wechat_bindings.sql`（`CREATE TABLE IF NOT EXISTS`）。启动顺序 = create_all → 逐条执行 migrations/*.sql，重复执行仅记 warning，幂等。
- 头像 **base64 直接入库**（解码后 ≤1MB，JPEG/PNG/WebP）：后端没有静态文件/上传体系，DB 存放 + data URI 下发最省事；个人主体 ≤15 个体验成员，体积可忽略（二期再迁文件存储）。

### 5.2 新端点 `POST /api/auth/wechat`

请求：`{code, invite_code?, nickname?, avatar_base64?}`（**无需 Authorization**，加入免鉴权清单；昵称 trim 后 ≤64 字；头像 base64 解码后 ≤1MB 且 mime ∈ JPEG/PNG/WebP——校验失败仅忽略该字段，不阻断登录）

流程：
1. `httpx` 调 `https://api.weixin.qq.com/sns/jscode2session?appid&secret&js_code&grant_type=authorization_code`（httpx 0.27.2 已在依赖里）
   - 微信侧返回 errcode / 5 分钟过期 / code 复用 → 统一 `401 {"detail":"微信登录失败，请重试"}`（前端收到后自动重新 wx.login 重试一次）
2. 查 `wechat_bindings.openid == openid` → 命中：直接对绑定用户 `create_access_token` 返回（后续访问路径）
3. 未命中（首次）：
   - `WECHAT_INVITE_CODE` 非空且 `invite_code` 缺失 → `403 {"detail":"invite_required"}`
   - 邀请码不匹配 → `403 {"detail":"invite_invalid"}`
   - 目标账号解析：`WECHAT_BIND_USERNAME` 指定（缺省取第一个 `is_super_admin=True` 的用户）→ 找不到 → `500 {"detail":"绑定账号未配置"}`
   - 插入 binding，签发 JWT 返回

响应：`{access_token, token_type, user, wx_profile: {nickname, avatar}}`（`avatar` 为 data URI 或 null；比 login 多 `wx_profile`，静默续登时客户端用它刷新本地资料）。

JWT 增发 `wx_openid` claim（扩展 `create_access_token` 加可选 extra_claims 参数，其他调用点不变）——供资料编辑接口定位绑定行；账号密码登录的 token 无此 claim，调资料接口返回 403。

### 5.4 资料编辑 `PATCH /api/auth/wechat/profile`（需 Authorization）

「我的」页改头像/昵称：`{nickname?, avatar_base64?}` → 按 JWT 的 `wx_openid` 定位绑定行并更新 → 返回 `{nickname, avatar}`。校验规则同 5.2。

### 5.3 新增 `.env` 变量（服务器）

```
WECHAT_APPID=wxe091ce737f45cacc
WECHAT_SECRET=<mp 后台「开发管理→开发设置」生成 AppSecret>
WECHAT_BIND_USERNAME=<库主账号用户名；留空=自动取超管>
WECHAT_INVITE_CODE=<6 位邀请码；留空=免验直进（体验版阶段默认留空；上架公开分发时必须设）>
```

## 6. 小程序端改动

| 文件 | 改动 |
|---|---|
| `utils/api.ts` | + `wechatLogin(code, inviteCode?)`（skipAuth） |
| `utils/auth.ts` | + `silentWechatLogin()`：wx.login → api.wechatLogin → setAuth + 存 `inflow_wx_profile` → token；403 invite_required 返回 `'invite'` 信号 |
| `app.ts` | `validateStored` 失败（无 token/过期/401）后不再跳登录页，先走 `silentWechatLogin()` 静默换发；仅 `invite`/失败时进登录页 |
| `pages/login/` | 改版（首次访问表单）：**头像选择**（`button open-type="chooseAvatar"`：微信头像/相册/拍照）+ **昵称**（`input type="nickname"`，键盘带微信昵称快捷填充）+ 邀请码输入框（**仅后端设了邀请码时出现**）+ 「微信一键登录」大按钮（微信品牌绿）；底部折叠「使用账号密码登录」保留原表单（管理员兜底，Web 端不变）。提交时 `FileSystemManager.readFile` 读临时头像为 base64 随 JSON 一并 POST（不走 multipart）。默认（无邀请码）形态下此页几乎不会被看到——静默链直接成功 |
| `utils/request.ts` | 401 时先尝试一次静默微信重登，成功则原请求重发；失败才跳登录页（防 token 中途过期打断阅读） |
| `pages/me/` | 展示微信头像+昵称（storage `inflow_wx_profile`，未设置回退账号用户名）+「编辑资料」复用 chooseAvatar / nickname 控件调 PATCH；「退出登录」保留（清本地 token，下次启动自动静默回归） |

`onShareAppMessage` 冷启动进入同样受益：被分享者首次输一次邀请码即可，之后永久无感。

## 7. 安全考量

- AppSecret 只存服务器 `.env`，小程序端永远只见临时 code（5 分钟、一次性）。
- `session_key` **不落库**（无用途；留存反而违反微信最小化原则）。
- 邀请码是唯一门禁：泄露后改 `.env` 重启即失效；已绑定 openid 不受影响（如需踢人，删 `wechat_bindings` 对应行）。
- JWT 体系、签名密钥、过期策略全部复用现状，不新增令牌类型。
- code2session 若 mp 后台开启了「IP 白名单」，需把服务器 IP `123.207.64.65` 加入。

## 8. 微信合规与审核考量

| 合规点 | 说明与对策 |
|---|---|
| wx.login 静默授权 | 无弹窗、无需用户点击同意，是平台标准登录能力，本身合规 |
| openid / 头像 / 昵称均属「用户信息」 | 上线前在 mp 后台填写**《用户隐私保护指引》**，声明收集「用户信息-微信 openid、头像、昵称」；`wx.login` / `chooseAvatar` / `type=nickname` 都是用户主动操作型能力，不触发隐私弹窗接口清单——头像昵称由用户亲手填写，正是 2022-10 平台回收静默获取后的官方替代路径，合规风险最低 |
| 首屏登录墙（主要被驳风险） | 已绑定用户静默直进、无感知；但**审核员**的微信未绑定且无邀请码 → 看到邀请码页，可能以「功能无法体验」驳回。对策（二选一）：① 提交审核时在「备注」提供体验邀请码 + 一句说明；② 审核窗口期把 `WECHAT_INVITE_CODE` 留空（免验直进），过审后再设码 |
| 「微信一键登录」按钮样式 | 微信品牌绿 + 明确文案，不仿造官方 UI、不使用微信 logo 变体；按钮真实触发微信登录 |
| 内容类目 | 沿用 MVP 方案建议：类目「工具>效率」、名称避开「资讯/媒体/社区」；聚合展示外部文章/播客在个人主体下有被判定为资讯属性的风险（与登录无关，一并提示，个人使用影响小） |
| 只用体验版分发（推荐初期形态） | **不上架发布就不触发审核**：个人主体体验成员上限约 15 人，自用+朋友足够；邀请码作为第二道门禁照常生效，后续要公开分发再走审核 |

## 9. 上线前置（人工步骤）

1. mp.weixin.qq.com → 开发管理 → 开发设置 → 生成 **AppSecret**（管理员扫码）
2. 同页若有「IP 白名单」开关：加入 `123.207.64.65`
3. mp 后台 → 设置 → 服务内容声明 → **用户隐私保护指引**：声明收集「用户信息（微信 openid、头像、昵称）」并提交生效（涉及审核时必须，纯体验版也建议先配好）
4. 服务器 `.env` 追加第 5.3 节四个变量 → `./start-server.sh --restart --detach`（新表自动创建）
5. 小程序端重新预览/体验版
