# 产品画布 · inflow-worker 重构 Skill 化

> 生成于 2026-08-23，基于产品讨论模式（完整讨论原文见 [20260823_01_worker重构Skill化产品讨论.md](20260823_01_worker重构Skill化产品讨论.md)）

## 一句话定义

为 inFlow 多用户内容知识库提供一套「云端交互展示 + 本地 Skill 执行」的投产架构：用户经微信 bot 投喂 URL/内容，云端登记任务，worker 上的渠道 Skill 完成抓取/转录/总结并将结构化结果入库，前端与微信 bot 读库展示。

## 目标用户

开放多用户使用的 C 端用户；使用频次较高、随用户量增长。每个用户每天 10 条免费转录额度（配额制，商业化空间预留）。

## 核心问题

1. **腾讯云网络限制**：cloud 端无法访问 Groq API（ASR 主力），耦合部署不可行，任务执行必须迁移到可自由出海的网络环境。
2. **NAT 后 worker 双向通信断裂**：worker（本地/无固定 IP）出站可达云端 DB，但 cloud 无法主动访问 worker——「任务下发」与「执行进度实时回传前端」两条链路没有解决方案，卡住投产。
3. **扩展性**：渠道（小宇宙、公众号、B 站……）持续新增，现有引擎整块 vendor 快照加渠道要动多处，维护成本高。

## 当前替代方案

现有 inflow-worker：轮询云端 PostgreSQL 认领 `external_processing` job，本地跑完整 pipeline（inflow_core 引擎快照），SFTP 回传渲染卡片。功能已跑通小宇宙/公众号链路，但通信架构未达投产要求，且引擎耦合不适应渠道快速扩展。

## 解决方案假设

**全局架构 = DB 唯一契约 + worker 主动出站轮询（几秒~十几秒粒度）+ Skill 化执行框架。**

核心假设：
- ① DB 轮询粒度（秒级~十几秒）足以同时承载任务分发、进度回传、结果入库三个方向——用户只需「知道它没死」；
- ② Skill 统一契约（`execute(job, context) → 结构化结果 + progress 回调`）能让新渠道以最低成本持续接入，且 A（代码插件）/B（Claude 会话）两种实现可互换。

**Skill 载体决策（已确认）**：A 为骨架（主链路渠道，确定性 Python 插件，复用现有 adapter/template 逻辑细节）、B 为长尾兜底（generic 位升级为 Claude 会话 + 指令包）、统一契约使两者在调度器眼里无差别。节奏：一期全 A 投产 → 二期 generic 位换 B → 此后新渠道先 B 试水、稳定后沉淀为 A（B 是 A 的孵化器）。

**重构方式（已确认）**：新起炉灶重建 worker 框架，但方案先行；现有引擎已趟坑的逻辑细节（小宇宙三层降级解析、ASR 落盘格式、状态机流转等）作为资产明确复用。

## 差异化优势

- 云/端完全隔离（仅 DB 契约），绕开云厂商网络限制的同时保留云端交互能力；
- Skill 化使渠道扩展从「改引擎多处」变为「新增一个自包含 Skill」；
- A/B 双形态执行器：确定性主链路 + agentic 长尾兜底，同一契约下可互换。

## 商业模式雏形

免费额度制：每用户每天 10 条免费转录，超出部分付费（定价未定）。成本主要在 worker 侧 ASR（Groq）+ LLM 调用，需建立每任务成本模型。

## 最大风险

1. 微信 bot 回推链路（个人号机器人封号风险 / 企业微信接口限制）——现状未验证；
2. 多用户高频与单 worker「暂不考虑并发」之间的吞吐矛盾——转录时延 × 机器规格无数字；
3. 免费额度 vs worker 侧 API 成本失衡，投产即亏损；
4. 7x24 机器选址未定（必须可出海访问 Groq），影响最终部署形态。

## 最小可行版本（MVP）

新 worker 框架 + DB 轮询通信链路（任务分发 + 秒级进度回传）+ 两个 A 形态 Skill（小宇宙播客转录、微信公众号抓取总结）端到端跑通，前端可实时展示 Job 状态，结果回推微信 bot。
