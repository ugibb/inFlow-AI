## 一、核心架构原则

### article_id 生成时机

通过 URL 验证后立即生成 `article_id`，而非等到 `displaying` 阶段。

```
URL 验证通过
   ↓
创建 Article stub（fetch_status='ingesting'）
创建 IngestJob（article_id 已设置）
   ↓
后台任务开始执行 → 采集 → 转录/规范化 → 章节 → AI解析 → 卡片 → 语义索引
   ↓
Article.fetch_status = 'completed'
```

**意义**：

- `/processing/[job_id]` 页面变为纯转发跳板，立即跳转至 `/read/{article_id}?job={job_id}`
- 处理中与完成后使用同一个阅读页 `/read/[id]`，仅增加 PipelineBar 显示差异

## 二、文章类型与管道路由（细粒度版）

PipelineBar 按**产物文件**展示步骤，不再使用「采集 / 转录 / AI解析 / 语义索引」等粗粒度标签。


| 类型            | Bar 节点数 | 步骤链                                                                         |
| ------------- | ------- | --------------------------------------------------------------------------- |
| 图文 / 电子书 / 报告 | **8**   | 资源下载 → 文本规范化 → 章节解析 → AI 解析 → 生成卡片 → HTML→PNG → 语义索引 → 完成                   |
| 音频            | **9**   | 资源下载 → 音频下载 → 转录 → 章节解析 → AI 解析 → 生成卡片 → HTML→PNG → 语义索引 → 完成               |
| 视频（预留）        | **11**  | 资源下载 → 视频下载 → 抽离音频 → 提取截图 → 转录 → 章节解析 → AI 解析 → 生成卡片 → HTML→PNG → 语义索引 → 完成 |
| 笔记（note）      | **待定**  | 简化链，后续单独定义                                                                  |


音频平台识别（`_AUDIO_PLATFORMS`）：`xiaoyuzhou`, `bilibili`（采集前即可推断）

### Bar UI 约束

- **单行展示，不换行**；节点数 9~11 个时采用压缩模式（短标签 + ✓ 图标）
- hover / Popover 展示完整步骤名、产物路径、最近 `step_logs` 日志
- 压缩模式示例：「资源」「音频」「转录」「章节」「解析」「卡片」「PNG」「索引」「完成」

## 三、状态机扩展

### 新状态图

```
图文路径:
pending → capturing → captured → normalizing → normalized
  → parsing → parsed → composing → composed → indexing → ready

音频路径:
pending → capturing → captured → transcribing → transcribed
  → parsing → parsed → composing → composed → indexing → ready

视频路径（预留）:
pending → capturing → captured → preprocessing → preprocessed
  → transcribing → transcribed → parsing → parsed
  → composing → composed → indexing → ready
```

> **说明**：`normalizing` / `composing` 为方案新增宏观状态，实现阶段可合并进 `transcribing` / `parsing` / `indexing`，Bar 仍按文件细步展示。详见「十一、进度判定策略」。

### 状态说明


| 旧状态          | 新状态             | 说明                            |
| ------------ | --------------- | ----------------------------- |
| `displaying` | `indexing`      | 语义嵌入索引步骤（更名）                  |
| —            | `transcribing`  | ASR 转录进行中                     |
| —            | `transcribed`   | 转录完成                          |
| —            | `normalizing`   | 图文 HTML → `_asr.txt` 提取（新增，方案；不写 `_asr.json`） |
| —            | `preprocessing` | 视频抽音频 + 截图帧（预留）               |
| —            | `preprocessed`  | 视频预处理完成（预留）                   |

| —            | `composed`      | 卡片生成完成（新增，方案）                 |
| —            | `cancelled`     | 用户主动取消（终态）                    |

## 四、代码复用策略

### 共用步骤模块 `app/core/pipeline/steps.py`

每个步骤函数签名统一：`(db, job_id, ...) → output_path`

```
app/core/pipeline/
├── state_machine.py     # 状态转换（扩展后）
└── steps.py             # 通用步骤函数
    ├── run_transcribe(...)        → asr_file_path（_asr.json）
    ├── run_normalize_text(...)    → asr_txt_path（图文，方案新增；仅写 _asr.txt）
    ├── run_chapters(...)          → chapters_file_path（方案新增/独立）
    ├── run_parse(...)             → parsed_file_path（{job_id}.json）
    ├── run_compose_card(...)      → html_path, png_path（方案新增）
    └── run_index(...)             → index_file_path（读 _asr.txt，写 _chunks.json）
```

### Orchestrator 路由逻辑（目标）

```python
# 图文 / 电子书 / 报告
asr_txt_path = await run_normalize_text(db, job_id, raw_file_path)  # 仅 _asr.txt
await run_chapters(db, job_id, raw_file_path)                        # 按 §12.3 自动探测 verbose → json/txt
parsed_path = await run_parse(db, job_id, raw_file_path, asr_txt_path=asr_txt_path)
await run_compose_card(db, job_id, raw_file_path, asr_txt_path=asr_txt_path, parsed_path=parsed_path)
await run_index(db, job_id, article_id, asr_txt_path, ...)

# 音频
# 采集阶段已下载媒体 → run_transcribe 读 01_ingest 下音频
asr_path = await run_transcribe(db, job_id, raw_file_path)
await run_chapters(db, job_id, raw_file_path)                        # 按 §12.3 自动探测 verbose → json
parsed_path = await run_parse(db, job_id, raw_file_path, asr_path)
await run_compose_card(...)
await run_index(...)

# 视频（预留）
# preprocess → 音频文件（保留实际扩展名）+ 截图 {job_id}_001.png … _NNN.png
audio_path = await run_preprocess_video(...)
asr_path = await run_transcribe(db, job_id, raw_file_path, audio_path=audio_path)
# 后续与音频相同
```

## 六、数据目录约定（修订）

```
data/
├── 01_ingest/
│   └── {platform}/{YYYYMMDD}/{index:03d}-{title_20}/
│       ├── {job_id}.json              ← RawCapture 元数据（资源下载产物）
│       ├── {job_id}.m4a               ← 音频下载（音频类）
│       ├── {job_id}.mp4               ← 视频下载（视频类，预留）
│       └── …                          ← 其他媒体扩展名按平台实际写入
│
├── 02_parse/
│   └── {platform}/{YYYYMMDD}/{index:03d}-{title_20}/
│       ├── {job_id}_asr.txt           ← 纯文本（转录 / 图文 HTML 提取；语义索引统一输入）
│       ├── {job_id}_asr.json          ← 音频转录结构化产物（图文类不生成）
│       ├── {job_id}_asr_verbose.json  ← 带时间戳分段（音频转录专用）
│       ├── {job_id}_chapters.json     ← 章节解析产物
│       ├── {job_id}.json              ← AI 解析产物（ParsedContent），非转录文件
│       └── {job_id}_chunks.json       ← 语义索引产物（Embedding 向量离线镜像）
│
└── 03_display/
    └── {platform}/{YYYYMMDD}/{index:03d}-{title_20}/
        ├── {job_id}.html              ← 卡片 HTML
        ├── {job_id}.png               ← 卡片 PNG
        └── {job_id}_NNN.png           ← 视频截图（NNN = 001…999，见 §12.4）
```

**关键约定**：

- `{job_id}.json` 在 `01_ingest` = RawCapture；在 `02_parse` = ParsedContent（AI 解析输出）
- 音频类：章节解析读 `_asr_verbose.json`（优先）或 `_asr.json`；AI 解析读 `_asr.json`；图文类下游读 `_asr.txt`（不生成 `_asr.json`）
- `{job_id}.json`（02_parse）是 AI 解析的**输出**，不是转录文件
- `_asr.txt` 是语义索引的统一输入；`{job_id}_chunks.json` 是语义索引的统一输出
- 路径推导：`02_parse` / `03_display` 通过替换 `01_ingest` 前缀得到，见 `conventions.py`

### 功能

- 按内容类型展示 8 / 9 / 11 个细粒度节点
- 每步状态：`pending` / `active` / `done` / `failed`

### 各类型步骤定义

#### 图文 / 电子书 / 报告（8 步）


| #   | 步骤名      | 输入                          | 产物（done 判定）                                    |

## 十、语义索引实现说明

**输入**：`02_parse/{job_id}_asr.txt`（全类型统一，纯文本）  
**输出**：`02_parse/{job_id}_chunks.json`

**`_asr.txt` 来源**：

| 类型 | 产出步骤 |
|------|---------|
| 音频 / 视频 | 转录步骤（与 `_asr.json`、`_asr_verbose.json` 一并写出） |
| 图文 / 电子书 / 报告 | 文本规范化步骤（从 RawCapture 提取正文写入） |

**流程**（`wiki_indexer.py` + `run_index`，目标实现）：

```
02_parse/{job_id}_asr.txt
        ↓
  读取全文（或截断至索引上限，如前 8000 字）
        ↓
  Embedding API（Siliconflow）或本地 fastembed → 512 维向量
        ↓
  写入 articles.embedding（pgvector，关联 article_id）
        ↓
  与同 user_id 库内文章算余弦距离，Top-5，阈值 0.45
        ↓
  写入 knowledge_edges（相关文章图谱）
        ↓
  写出 02_parse/{job_id}_chunks.json（text + embedding 离线镜像）
```

**与当前代码的差异**：现有 `wiki_indexer` 从 ParsedContent / Article（title + summary + 正文）取文本；重构后改为直接读 `_asr.txt`，与章节 / AI 解析 / 卡片步骤解耦。

**特性**：

- 非致命：索引失败不阻断 `ready`，日志记录「无向量」
- 幂等：可安全重跑

**Bar 判定**：`02_parse/{job_id}_chunks.json` 存在且 size > 0 → done

## 十一、进度判定策略

### 问题：为何不只靠「文件是否存在」？


| 场景                  | 仅看文件            | 需要补充                            |
| ------------------- | --------------- | ------------------------------- |
| 步骤已完成               | ✅ 文件存在          | —                               |
| 重试 / 重启恢复           | ✅ 跳过已有文件        | —                               |
| **进行中**（LLM 30~90s） | ❌ 文件尚未写出，像「未开始」 | 粗 `job.status`                  |
| **失败**              | ❌ 旧文件可能残留       | `status=failed` + `error_stage` |
| **同宏观阶段多步**         | ⚠️ 需组合判断        | 文件链式推断（有 json 无 m4a → 停在音频下载）   |


### 推荐：**文件判定为主 + 粗 status 补 running/failed**

```
步骤状态 =
  if job.status == 'ready'                    → 全部 done
  if job.status == 'failed'                   → 按 error_stage + 文件推断 failed 步
  if 该步产物文件存在且 size > 0               → done
  elif job.status 属于该步宏观阶段              → active（转圈）
  else                                        → pending
```

**不需要**：

- 单独的 `pipeline_steps[]` DB 字段持久化
- 用 `step_logs` 驱动状态机（`step_logs` 仅用于 hover 展示实时日志）

**后端 API**：`GET /api/ingest/jobs/{id}` 返回时**即时计算** `pipeline_steps[]`（扫盘 + 读 job.status），前端只渲染。

### 宏观 status → 细步 active 映射（示例 · 音频）


| job.status     | active 细步（第一个未完成文件的步骤） |
| -------------- | ---------------------- |
| `capturing`    | 资源下载 或 音频下载（按文件组合）     |
| `transcribing` | 转录                     |
| `parsing`      | 章节 / AI 解析（按文件组合）      |
| `composing`    | 卡片 / PNG               |
| `indexing`     | 语义索引                   |

### 12.1 图文「文本规范化」 ✅ 已确认

**决策**：新增 `run_normalize_text` 步骤，从 `01_ingest/{job_id}.json`（RawCapture）提取 `raw_html` / `raw_text`，**仅写入** `02_parse/{job_id}_asr.txt`。

- **写 `_asr.txt`**：HTML 需去标签提取正文，与语义索引输入对齐，下游步骤统一读纯文本。
- **不写 `_asr.json`**：该文件是 ASR 转录的结构化产物（分段、时长等），图文无对应语义，强行对齐无价值。
- **下游差异**：图文路径的 AI 解析 / 卡片生成读 `_asr.txt`；音频路径读 `_asr.json`；章节解析输入见 §12.3

### 12.2 卡片与 ready 的关系 ✅ 已确认（方案 A）

**决策**：采用 **方案 A · 阻塞**——`job.status = ready` 前必须完成卡片 HTML + PNG 两步；微信 Bot **不再负责渲染**，仅做 CDN 推送。

| 项 | 约定 |

| `ready` 判定 | `html` + `png` 文件均存在且 size > 0，且语义索引完成（索引失败见 §10 非致命策略） |
| 微信 Bot | 读取已有 `html` / `png`，上传 CDN 后推送；无产物时不触发渲染兜底 |
| PipelineBar | 「生成卡片」「HTML→PNG」「完成」与主链路一致，无异步滞后步 |

- ~~C. 维持现状~~：主 pipeline 不生成卡片，仅 wechat 触发时渲染

### 12.3 章节解析输入细节 ✅ 已确认

**输入文件优先级**（全类型统一，`run_chapters` 按序探测）：

| 优先级 | 文件 | 适用 |
|--------|------|------|
| 1（默认） | `_asr_verbose.json` | 音频 / 视频转录产物，含 `segments` + 时间戳 |
| 2（回退） | `_asr.json` | verbose 不存在时的音频 / 视频兜底 |
| 2（回退） | `_asr.txt` | verbose 不存在时的图文兜底（文本规范化产物） |

**送入章节 LLM 的转写格式**：

| 场景 | 段首标注 |
|------|----------|
| 读到 `_asr_verbose.json` | 按 segment 注入真实时间戳 `[HH:MM:SS]`（与现有 `_build_timestamped_transcript` 一致） |
| 回退 `_asr.json` / `_asr.txt`（无时间戳） | 全文按固定窗口或自然段切分，段首标注 `第一段`、`第二段`、…、`第n段` |

**实现要点**：

- `run_chapters` 封装上述探测与格式化逻辑，对上游 orchestrator 透明
- 章节 LLM prompt 需兼容两种标注（时间戳 / 第n段），`start_time` 在无时间戳时可填 0 或由 LLM 按段序估算
- 产物仍为 `02_parse/{job_id}_chapters.json`，结构不变

### 12.4 视频预处理产物命名 ✅ 已确认

**抽离音频**

- 命名：`01_ingest/{job_id}.{ext}`，**保留实际扩展名**（如 `.mp3`、`.m4a`、`.wav`），不强制改写为 `.mp3`
- 转录步骤直接读该文件，扩展名由 ffmpeg / 平台决定

**视频截图**

- 数量：按预处理策略截取 **n 张**（n 由时长 / 章节 / 配置决定，非固定 1 张）
- 命名：`03_display/{job_id}_{NNN}.png`，`NNN` 为三位零填充序号 **001、002、…、999**
- 示例：`{job_id}_001.png`、`{job_id}_002.png`、…、`{job_id}_012.png`
- **done 判定**：`001` ~ `00n` 连续齐全（至少存在 `_001.png`；完整 done 为 n 张全部写出）
- 与卡片 PNG（`{job_id}.png`）区分：截图带 `_NNN` 后缀，卡片无后缀
