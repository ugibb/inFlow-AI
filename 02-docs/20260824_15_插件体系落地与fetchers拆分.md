## 1. 插件体系落地（对应蓝图 §4.3）

### 1.1 目录地图（`backend/plugins/`，16 个 .py，核心骨架约 600 行）

| 文件 | 职责 |
|------|------|
| `base.py` | `Plugin` 基类契约 + `PluginStatus` 枚举（id/name/kind/auto_start/enabled） |
| `registry.py` | `BUILTIN_PLUGINS` 内置插件注册表（wechat / obsidian） |
| `manager.py` | `PluginManager` 单例 `plugin_manager`——启动期注册、启停调度、快照 |
| `process.py` | 进程型插件子进程管理：`start_bot` / `stop_bot` / PID 文件读写 |
| `status.py` | 存活判定：`process_is_alive`（含僵尸检测）、`pid_file_status` |
| `states.py` | `plugin_states` 表读写：`get_enabled` / `set_enabled` |
| `router.py` | 管理 API：`GET /api/plugins` + `POST /{id}/start|stop|restart` |
| `wechat/plugin.py` | `WechatPlugin`（kind=process，auto_start=true，无 API 路由） |
| `wechat/bot.py` | 微信 bot 主循环（子进程入口 `python -m backend.plugins.wechat.bot`） |
| `wechat/router.py` | 微信推送收件端点（进程内亦可走 HTTP，双路径） |
| `wechat/ilink_media.py` | ilinkai 媒体对接 |
| `obsidian/plugin.py` | `ObsidianPlugin`（kind=api，enabled 开关控制，`routers()` 返回 obsidian router） |
| `obsidian/router.py` | Obsidian 同步端点（`/api/obsidian/...`） |

### 1.2 启动期装配（`backend/main.py`）

```
lifespan.startup
  └─ plugin_manager.startup()
       ├─ 注册 BUILTIN_PLUGINS
       └─ 对 auto_start 的进程型插件：探测已存活（PID 文件）→ 未存活则 start_bot
lifespan.shutdown
  └─ plugin_manager.shutdown() → 停止所有进程型插件（优雅 SIGTERM → 超时 SIGKILL）
```

路由挂载：
```
app.include_router(plugins_router)              # 管理端点（require_superadmin）
for _plugin in plugin_manager.all():
    if _plugin.kind == "api":
        _deps = [Depends(_require_plugin_enabled(_plugin.id))]   # 停用 → 503
    for _r in _plugin.routers():
        app.include_router(_r, dependencies=_deps)
```

### 1.3 双路径兼容（重点）

- **start-server.sh 直跑 bot**：写旧规范 PID 文件 `.server/wechat-bot.pid`；PluginManager 探测到存活即识别为 `running`，**不重复拉起**。
- **PluginManager 启停**：写新规范 `.server/plugins/{id}.pid`，同时兼容探测旧文件。
- `process.start_bot` 的 cwd 必须是 `03-src/`（backend 包唯一可见目录）——否则 `python -m backend.plugins.wechat.bot` 直接 ModuleNotFoundError。

### 1.4 验证结论（阶段 4-6 实测）

| 场景 | 结果 |
|------|------|
| obsidian enabled=true → sync 200 | ✅ |
| obsidian stop → 503（`_require_plugin_enabled` 拦截） | ✅ |
| obsidian start → 200 | ✅ |
| wechat auto_start → 真实子进程拉起（PID 文件落盘） | ✅ |
| wechat stop → `stopped=true` + 进程退出 + PID 清理 | ✅ |
| wechat start → running + 进程拉起 | ✅ |
| backend SIGTERM → shutdown → bot 优雅停止 + PID 清理 | ✅ |
| 僵尸进程误判 | ✅ 修复（`status._is_zombie` 用 `ps -o stat=` 检 Z） |

### 1.5 已知约束

- 停用插件 = 关 API 型路由（503）；进程型没有「停用」，只有 stop（`not_configured` 时按钮置灰）。
- dev 降级鉴权（非 `inFlow_ENV=production` 时无 token 请求返回第一个 active 用户）是项目既有行为，插件管理页的 200 属预期，非 bug。

### 2.3 装饰器边界修复（切割时最深的坑）

按方法行号切割时，装饰器行与方法定义行跨段被切开，静默丢失/错配 `@staticmethod`/`@classmethod`——语法可能合法但运行时参数错位。**判定依据：反汇编原文件 pyc 的字节码**（`LOAD_NAME staticmethod` 紧跟的 `STORE_NAME` 才是被装饰方法）。

| 方法 | 原始装饰器 | 切割后症状 | 修复 |
|------|-----------|-----------|------|
| `_extract_feishu_doc_title` | `@classmethod`（装饰器 304 被切到 base 段） | feishu.py 缺装饰器 | feishu.py 补 `@classmethod` |
| `_text_len` | `@staticmethod`（装饰器 496 被切到 feishu 段） | base.py 误挂 `@classmethod`（304 的） | base.py 改 `@staticmethod` |
| `_build_generic_result` | **无装饰器**（实例方法） | 被误判为 staticmethod | 保持实例方法（调用方全是 `self.` 前缀） |
| `_clean_srt` | `@staticmethod` | 在段内，正确保留 | 无需处理 |

> 教训：切割大文件后不能只 `py_compile` 过就算完——装饰器语义、段边界函数归属都必须用「MRO `__dict__` 查包装器 + 实际调用」验证。
