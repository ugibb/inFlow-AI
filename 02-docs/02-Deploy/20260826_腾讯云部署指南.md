# inFlow AI — 腾讯云部署指南（2026-08 新形态）

> 本文档针对**当前部署形态**编写：**云端 infra 容器 + 宿主机直跑 backend/bot + 本地 worker 承接重计算**。
> 旧的「Docker 全容器」宝塔方案已于 2026-08-20 移除（`02-docs/DEPLOY_BAOTA*.md` 均带废弃横幅，仅作历史参考）。
> 逐步操作、可直接复制命令。建议从上到下依次执行。

---

## 0. 部署形态概览（必读）

### 0.1 云端单元结构

```
                    用户浏览器 / 微信 / Obsidian
                              │
                              ▼
                ┌─────────────────────────────┐
                │  宝塔 Nginx  :80 / :443     │ ← 域名、HTTPS、反向代理
                │  （仅转发，不跑业务）        │
                └─────────────┬───────────────┘
                              │  反代 → 127.0.0.1:8080
                              ▼
                ┌─────────────────────────────┐
                │  容器 Nginx :8080（Docker）  │ ← 只绑本机回环，避开宝塔 80/443
                │    ├─ /        → frontend:3000
                │    └─ /api/    → host.docker.internal:8000（宿主机 backend）
                └─────────────────────────────┘
                              │
    ┌─────────────────────────┼─────────────────────────┐
    ▼                         ▼                         ▼
┌─────────────┐          ┌─────────────┐          ┌─────────────┐
│  frontend   │          │  postgres16 │          │  redis7     │
│ Next.js 14  │          │ +pgvector   │          │ (缓存)      │
│ 容器 :3000   │          │ 容器 :5432   │          │ 容器 :6379  │
└─────────────┘          └─────────────┘          └─────────────┘
       宿主机直跑进程（不是容器）：
       ├─ backend  uvicorn :8000   （日志 04-log/backend/）
       └─ wechat-bot python -m bot （日志 04-log/wechat-bot/）

重计算 pipeline（采集/转录/parse/compose/截图）
       ↓  由本地 worker 承接（独立仓库 ugibb/inflow-worker）
```



### 0.2 谁管什么


| 组件                                  | 形态            | 管理方式                                                               |
| ----------------------------------- | ------------- | ------------------------------------------------------------------ |
| postgres / redis / nginx / frontend | Docker 容器     | `docker compose`                                                   |
| backend（FastAPI :8000）              | 宿主机直跑         | `start-server.sh`（PID 在 `.server/`）                                |
| wechat-bot                          | 宿主机直跑         | `start-server.sh`（PID 在 `.server/`）                                |
| 重计算 pipeline                        | **本机** worker | 独立仓库 [ugibb/inflow-worker](https://github.com/ugibb/inflow-worker) |




### 0.3 端口规划（关键）


| 端口       | 绑定           | 谁用                    | 腾讯云安全组                                 |
| -------- | ------------ | --------------------- | -------------------------------------- |
| 22       | 0.0.0.0      | SSH                   | ✅ 放行（建议白名单）                            |
| 80 / 443 | 0.0.0.0      | 宝塔 Nginx（对外）          | ✅ 放行                                   |
| 8080     | 127.0.0.1 回环 | 容器 Nginx              | ❌ 不放行（仅本机）                             |
| 8000     | 0.0.0.0      | backend 直跑            | ❌ 不放行（nginx 经 Docker 网桥访问）             |
| 5432     | 0.0.0.0      | **本地 worker 连接云端 PG** | ⚠️ 仅白名单放行本地 Mac 公网 IP，**切勿 0.0.0.0/0** |
| 6379     | 127.0.0.1 回环 | redis                 | ❌ 不放行                                  |

## 2. 服务器环境安装



### 2.1 安装 Git

```bash
dnf install -y git
```



### 2.2 安装 Docker + Compose v2

OpenCloudOS 9 / CentOS 用腾讯云镜像源安装：

```bash
dnf install -y dnf-utils
dnf config-manager --add-repo https://mirrors.cloud.tencent.com/docker-ce/linux/centos/docker-ce.repo
dnf install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
systemctl enable --now docker
```

验证：

```bash
docker --version
docker compose version   # 必须输出 v2（含 "Docker Compose version v2..."）
```

> 也可以用宝塔「软件商店 → Docker 管理器」安装（二选一即可，无需重复装）。
> 若 `docker compose` 报找不到命令，说明缺 `docker-compose-plugin` 包。



### 2.3 安装 Python（backend venv 用）

OpenCloudOS 9 自带 Python 3.9，可直接使用（本项目依赖兼容 3.9+，建议 3.10+）：

```bash
# 方案 A：用系统自带 python3（最省事，OpenCloudOS 9 默认 3.9）
dnf install -y python3 python3-pip python3-devel gcc gcc-c++ make

# 方案 B（推荐，若想要 3.10+）：安装 python3.11
dnf install -y python3.11 python3.11-pip python3.11-devel gcc gcc-c++ make
```

> `gcc` 用于个别无预编译 wheel 的包兜底编译（本项目依赖基本都有 wheel，装上更保险）。
> 记录一下你的 python 解释器路径，第 4 步会用。方案 A：`python3`；方案 B：`python3.11`。



### 2.4 安装 OpenSSL 命令行工具

启动脚本用 `openssl rand` 生成密码/密钥，一般系统自带；确认一下：

```bash
openssl version
```

## 5. 首次启动



### 5.1 配置 `.env`（二选一）



#### 方式一（推荐）：手动复制，密钥交脚本补全

```bash
cd /www/wwwroot/inflow-ai
cp .env.example .env
```

首次运行启动脚本时，若 `.env` 中仍是 `change_me` 占位，会自动用 `openssl` 生成并替换这三项：
`POSTGRES_PASSWORD`、`SECRET_KEY`、`SERVICE_TOKEN_WECHAT_BOT`；同时写入 `SERVICE_TOKENS`，
并把生产 `INFLOW_PIPELINE_DATA_DIR` 设为 `/www/data/inflow/pipeline`（自动建目录）。

> 新版 backend 连接串由代码按 `POSTGRES_PASSWORD` 自动拼，**无需再手动配置 `DATABASE_URL`**；
> 若旧 `.env` 残留 `change_me` 占位的 `DATABASE_URL`/`DATABASE_URL_SYNC`，请删除这两行
> （保留会因「占位 DSN」触发 `InvalidPasswordError`，见第 9 节故障排查）。

#### 方式二：跳过本节，直接执行第 5.3 步启动命令

脚本检测到 `.env` 不存在/占位时，会**自动完成**复制 + 生成密钥的全部动作，无需手动操作。

> 想现在手动生成密钥，而不是等脚本？执行：
>
> ```bash
> openssl rand -base64 24 | tr -d '/+=' | head -c 32   # 输出 → 用作 POSTGRES_PASSWORD
> openssl rand -base64 48 | tr -d '/+=' | head -c 48   # 输出 → 用作 SECRET_KEY
> nano .env                                             # 替换 change_me 占位后保存
> ```



### 5.2 检查 `.env` 必填项

```bash
cd /www/wwwroot/inflow-ai
grep -E "^(POSTGRES_PASSWORD|SECRET_KEY)=" .env
```

确认两项均**非** `change_me` 占位（脚本首次运行已自动生成真实值）：

- `POSTGRES_PASSWORD` —— postgres 建库密码，数据库唯一必填项
- `SECRET_KEY` —— JWT 签名密钥

> 新版**不再需要配置** `DATABASE_URL` / `DATABASE_URL_SYNC`：backend 连接串由代码按
> `POSTGRES_*` 组件自动拼（host=localhost、user/db=inflow、port=5432 均为固定默认值），
> 从根上消除了「建库密码与连接密码不一致」导致 502 的隐患。
>
> 旧部署兼容：若 `.env` 残留显式 `DATABASE_URL`（非 `change_me` 占位），仍会优先采用；
> 若是 `change_me` 占位则自动忽略，改走组件拼（见 `backend/core/config.py` 的 `resolved_database_url`）。

### 5.3 启动（后台运行）

```bash
cd /www/wwwroot/inflow-ai
./start-server.sh --detach --verify
```

脚本会依次：

1. 构建前端镜像 `docker compose up -d --build --force-recreate frontend`（⏱️ 首次构建约 5–15 分钟，含 `npm ci` + `next build`，国内走 npmmirror 镜像）
2. 拉起 nginx / postgres / redis 容器
3. 停掉旧直跑进程 → 启动 backend（uvicorn :8000）→ 启动 wechat-bot
4. 健康检查 `http://127.0.0.1:8080/api/health`



### 5.4 验证部署成功

```bash
# 1) 容器状态：4 个容器都 Up
docker compose ps

# 2) 健康接口（本机直接 curl）
curl http://127.0.0.1:8080/api/health
# 期望返回 JSON，含 "status" 字段

# 3) 直跑进程
cat .server/backend.pid | xargs ps -o pid,etime,cmd -p
cat .server/wechat-bot.pid | xargs ps -o pid,etime,cmd -p

# 4) 日志无报错
cd /www/wwwroot/inflow-ai
tail -20 04-log/backend/$(date +%F).log
```

> 数据库表在 backend 首次启动时**自动创建**（`init_db` 幂等执行全部 `migrations/*.sql`，无需手动建表）。

## 6. 域名 + HTTPS + 反向代理（宝塔）

> 若你已有宝塔面板，直接跳到 6.3。纯命令行替代方案见文末[附录 A](#附录-a不用宝塔怎么办)。



### 6.1 安装宝塔面板（如未装）

OpenCloudOS 9 / CentOS 用官方一键脚本安装（若[宝塔官网](https://www.bt.cn)有更新命令，以官网为准）：

```bash
curl -sSf https://download.bt.cn/install/install_panel.sh | bash
```

安装完成后：

- 终端会打印**面板地址、账号、初始密码**，先记下来
- 浏览器打开面板地址（形如 `http://<公网IP>:<面板端口>/<随机路径>`），首次访问修改登录密码
- 面板内若提示安装运行环境，**不要**装 MySQL/MariaDB/Nginx 等——本项目只用到面板的 Nginx 反代功能



### 6.2 放行安全组端口

**腾讯云控制台操作**：云服务器控制台 → 该实例 → **安全组** → 编辑规则 → 添加入站规则：


| 方向  | 端口  | 来源        | 用途    |
| --- | --- | --------- | ----- |
| 入站  | 80  | 0.0.0.0/0 | HTTP  |
| 入站  | 443 | 0.0.0.0/0 | HTTPS |
| 入站  | 22  | 你的 IP     | SSH   |


**宝塔防火墙同步放行**：宝塔 → 左侧「安全」→ 放行端口 → 分别放行 `80`、`443`。

**验证端口已开**（服务器本机执行）：

```bash
ss -lntp | grep -E ':(80|443)\b'   # 期望看到 nginx 在监听 80/443
```



### 6.3 宝塔添加网站 + 反向代理

1. 宝塔 → **网站** → **添加站点**
  - 域名：`你的域名.com`（带不带 www 按需，可后补）
  - 类型：纯静态（不需要 PHP/数据库）
2. 进入该站点 → **反向代理** → 添加反向代理：
  - 代理名称：`inflow`
  - 目标 URL：`http://127.0.0.1:8080`
  - 发送域名：`$host`（默认）
3. 保存后，先在**服务器本地**验证反代链路通（带 Host 头直连容器 Nginx）：
  ```bash
   curl -H "Host: 你的域名.com" http://127.0.0.1:8080/ -o /dev/null -w "HTTP %{http_code}\n"
   # 期望输出 HTTP 200
  ```
4. 再用浏览器访问 `http://你的域名.com`，应能看到 inFlow 登录页。



### 6.4 申请 SSL 证书开启 HTTPS

宝塔 → 该站点 → **SSL** → Let's Encrypt → 一键申请并开启**强制 HTTPS**。

验证证书已匹配本站点（任意机器执行）：

```bash
echo | openssl s_client -connect <公网IP>:443 -servername 你的域名.com 2>/dev/null \
  | openssl x509 -noout -subject -dates
# 期望：subject CN=你的域名.com，且 notAfter 在未来（未过期）
```

之后 `https://你的域名.com` 应正常访问。

### 6.5 回填公网地址（重要）

微信 Bot 精华卡外链、部分回调 URL 依赖公网地址。修改 `.env`：

```bash
cd /www/wwwroot/inflow-ai
sed -i 's|^inFlow_PUBLIC_BASE=.*|inFlow_PUBLIC_BASE=https://你的域名.com|' .env
grep '^inFlow_PUBLIC_BASE=' .env
```

重启生效：

```bash
./start-server.sh --restart --detach --verify
```

> 若已有微信绑定过的用户，重启 bot 后绑定心跳会重新建立，无需重新扫码。

## 7. 本地 worker 对接

云端只负责「入口 / 存储 / 展示」，真正的**采集 / 转录 / parse / 知识图谱 / 截图**由你的本地电脑上的 worker 承接。

### 7.1 安全组放行 5432（白名单）

腾讯云控制台 → 安全组 → 添加规则：


| 方向  | 端口   | 来源                 | 用途                |
| --- | ---- | ------------------ | ----------------- |
| 入站  | 5432 | **你的本地 Mac 公网 IP** | 本地 worker 直连云端 PG |


> ⚠️ **只填本地公网 IP，禁止 0.0.0.0/0**。查本地公网 IP：
>
> ```bash
> curl ifconfig.me    # 在你的 Mac 上执行
> ```



### 7.2 本地 worker 部署

worker 是**独立工程**，在**本机（Mac）**执行：

```bash
git clone https://github.com/ugibb/inflow-worker.git
cd inflow-worker
cat README.md          # 按 README 配置 .env 与启动方式（start-worker.sh）
```

**先验证本机到云端 PG 连通**（Mac 上执行，确认 7.1 安全组已放行你的公网 IP）：

```bash
curl ifconfig.me       # 记录输出的公网 IP（用于 7.1 白名单）
nc -z -w 5 <云端公网IP> 5432 && echo "5432 可达 ✅" || echo "5432 不通 ❌"
```

对接要点：

- worker 的 `DATABASE_URL` 指向云端：`postgresql://inflow:<密码>@<云端公网IP>:5432/inflow`
- url / upload / paste 三入口默认 `EXTERNAL_PROCESSING=true`，云端只登记、worker 认领执行
- worker 未运行/失联时，云端新任务停在 `pending`（前端可见，**不会静默丢**）

```bash
mkdir -p /www/backup

```bash
crontab -e

0 3 * * * docker exec inflow-db pg_dump -U inflow inflow > /www/backup/inflow_$(date +\%F).sql && find /www/backup -name 'inflow_*.sql' -mtime +30 -delete
```

### 8.5 部署后自检清单

部署完成后，建议按下面 3 步做一遍最终体检（2026-08-26 实盘诊断沉淀）：

#### ① 域名解析是否指向本服务器

```bash
# 用公网 DNS 验证（本机可能被代理工具的 fake-ip 干扰，勿看 dig 默认结果）
dig @223.5.5.5 +short inflow.huituai.site A
# 期望输出：你的腾讯云服务器公网 IP（例：123.207.64.65）
# 若出现 198.18.0.x 之类的保留地址，说明是本机代理的假解析，非真实状态
```



#### ② HTTPS 证书是否匹配本站点

```bash
echo | openssl s_client -connect <公网IP>:443 -servername inflow.huituai.site 2>/dev/null \
  | openssl x509 -noout -subject -dates
# 期望：subject CN=inflow.huituai.site，且 notAfter 在未来（未过期）
# 若 subject 是别的域名（如 api.cike.huituai.site），说明 443 命中了其他站点的
# default server，需在宝塔确认本站点 SSL 的 server_name 绑定正确
```



#### ③ 公网只该放行 22 / 80 / 443（+ 5432 白名单）

```bash
for p in 22 80 443 5432 8000 8080; do nc -z -w 3 <公网IP> $p >/dev/null 2>&1 \
  && echo "端口 $p: 开放" || echo "端口 $p: 关闭"; done
# 期望：5432 若从公网能连，说明安全组是全放行（危险），务必收紧为本地 Mac IP 白名单；
#       8000 / 8080 不应在公网出现——收紧后应变为「关闭」

## 9. 故障排查


| 现象 | 排查 |
| --- | --- |
| `./start-server.sh` 报「未找到 backend venv」 | 没做第 4 步，先建 venv 装依赖 |
| 健康检查超时 | `tail -50 04-log/backend/$(date +%F).log`；多半是依赖没装全，或 backend 连不上 postgres（InvalidPasswordError 见下行） |
| backend 报 `password authentication failed for user "inflow"` | 旧 `.env` 残留 change_me 占位 DSN——删除 `.env` 中 `DATABASE_URL`/`DATABASE_URL_SYNC` 两行（连接串由代码按 `POSTGRES_PASSWORD` 自动拼），重跑 `./start-server.sh` |
| `docker compose ps` 里 postgres 反复重启 | `.env` 中 `POSTGRES_PASSWORD` 为空/不一致，或端口 5432 被本机占用 |
| 前端构建 OOM / 失败 | 4GB 机器正常，Dockerfile 已限 2048MB；内存不足可临时加 swap |
| 前端能开但 `/api` 502 | ① 先看 backend 日志确认 backend 活着（`tail -50 04-log/backend/$(date +%F).log`）；② 若 nginx.conf 仍用「变量+resolver」反代 `host.docker.internal`（旧版）——该域名是 extra_hosts 写进 /etc/hosts 的静态映射，Docker DNS（resolver 127.0.0.11）查不到，必须用普通 `proxy_pass`：`git pull` 后 `docker compose up -d --force-recreate nginx`；③ 再 `docker compose restart nginx` |
| 域名打不开 | ① 安全组 80/443 未放行 ② 宝塔站点反向代理目标是否 `127.0.0.1:8080` ③ 强制 HTTPS 后是否用 https 访问 |
| HTTPS 打不开 / 返回 404 | 443 命中了其他站点的 default server 或证书过期——宝塔 SSL 里确认本站点 `server_name` 绑定正确、证书未过期（`openssl s_client` 查 subject），重新开启强制 HTTPS |
| 微信发消息 bot 不回 | `tail -20 04-log/wechat-bot/$(date +%F).log`；确认 `.env` 里 `SERVICE_TOKEN_WECHAT_BOT` 与 `SERVICE_TOKENS` 一致 |
| 新任务一直 pending | worker 未连上：本机 worker 是否在跑、安全组 5432 是否放行本地 IP、worker 的 DSN 是否正确 |
| 免费额度提示 429 | 当日到 `ready` 的 job 已达 `FREE_QUOTA_PER_DAY`（默认 10），次日恢复；自托管可设 `FREE_QUOTA_PER_DAY=0` 取消限制 |
| 观测告警刷 WARNING/ERROR | `observer.py` 巡检命中（worker 失联/进度停滞等），属正常告警；无需可设 `OBSERVER_ENABLED=false` |
| 公网能连到 5432 / 8000 / 8080 | 安全组放行过宽（危险）——仅保留 22/80/443，5432 收紧为本地 Mac IP 白名单，8000/8080 应关闭（详见 8.5 自检 ③） |
| backend 启动报 `[Errno 98] address already in use` | 端口 8000 已被旧 backend 实例占用（重复启动/进程未停干净）——`pkill -f "uvicorn backend.main"` 后重跑 `./start-server.sh --detach --verify` |
| 刚 recreate 后 curl 报 `Connection reset by peer` | nginx 容器尚未就绪——`sleep 2` 后重试即恢复；持续失败再 `docker compose restart nginx` |
| compose 启动报 `Found orphan containers ([inflow-backend inflow-wechat-bot])` | compose 已移除服务的旧容器仍存活（2026-08-20 前架构遗留），重复连库、浪费资源——`docker compose up -d --remove-orphans` 一键清理 |
| 公网 IP:8080 打不开 | **正常，非故障**：容器 nginx 只绑 `127.0.0.1:8080` 回环（安全设计，避开宝塔 80/443），公网必须走宝塔反代；与安全组无关（放行也连不上） |
| 日志每行内容出现两次 | 无害噪音：`LOG_TO_STDOUT=1` 与 nohup 重定向双写同一文件所致，忽略即可 |
| 域名能开但担心走的是旧 Docker 部署 | 验证链路：`curl -s http://域名/api/health` 应返回 `{"status":"ok","app":"inFlow AI"}`（宿主新 backend）；`curl -si http://域名/` 应见 `X-Powered-By: Next.js`（新 frontend 构建）。旧 backend/bot 容器不在新链路（详见 8.5 ④） |

## 附录 A：不用宝塔怎么办

容器 Nginx 默认只绑 `127.0.0.1:8080`（为了避开宝塔的 80/443）。不用宝塔时二选一：

### 方案 A1（推荐）：宿主机 Nginx 反代

```bash
# 1) 安装 Nginx
dnf install -y nginx

# 2) 写入站点配置（反代到容器 Nginx 127.0.0.1:8080）
cat > /etc/nginx/conf.d/inflow.conf <<'EOF'
server {
    listen 80;
    server_name 你的域名.com;

    client_max_body_size 500m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
EOF

# 3) 启动并自启
systemctl enable --now nginx
nginx -t && systemctl reload nginx

# 4) 申请 SSL（certbot 自动配 HTTPS 与跳转）
dnf install -y certbot python3-certbot-nginx
certbot --nginx -d 你的域名.com
```

安全组需放行 80/443。

### 方案 A2：让容器 Nginx 直接对 80

编辑 `docker-compose.yml` 的 nginx 端口映射：

```yaml
ports:
  - "80:80"     # 原来: "127.0.0.1:8080:80"
```

然后 `docker compose up -d --force-recreate nginx`，域名 A 记录直接指到服务器 IP。HTTPS 需额外处理。
