# inFlow AI — 「内容直写 articles 表」上线执行方案（2026-08-30）

> **一句话**：worker 处理结果（chapters / transcript / 精读 HTML / 音频链接等）不再依赖云端磁盘文件，改为 worker 三阶段直写 `articles` 表，云端接口改读 DB 字段——修复阅读页「章节速览 / AI 精读 / 全文转录 / AI 解析」四个 tab 在新管线下全部 404 的问题。
>
> 关联提交：云端 `e4f65ab`（inFlow-ai）、worker `230969c`（inflow-local）。
> 适用环境：腾讯云 `/www/wwwroot/inflow-ai`（容器 infra + 宿主机直跑 backend）+ 本地 Mac worker。
> 全程约 15 分钟 + 一条端到端验证任务的处理时长。

---

## 0. 背景速览（为什么有这次上线）

**问题根因**：worker 重构（Skill 化）后，SFTP 回传范围收敛为仅「卡片 PNG + HTML」两个文件；
但云端 `chapters / transcript / deep-read` 三个接口仍按旧管线逻辑去读云端磁盘上的
`02_parse/*_chapters.json`、`*_asr_verbose.json` 等文件——这些文件不再上云，接口必然 404。

**方案**（已落地，本次只做部署）：DB 是唯一内容交付通道。

| worker 写入时机 | 直写字段 |
| --- | --- |
| capture 后 | `raw_content`（原始正文）、`media_url`（音频 CDN 链接） |
| parse 后（→ parsed） | `title / summary / key_points / clean_content / plain_text / word_count / reading_time / author`、`chapters`（富格式整包） |
| ready 前（index 后） | `transcript`、`deep_read_html` |

配套：`articles` 表新增 3 列（022 迁移）；云端三接口弃文件读库；前端音频加载失败自动降级
「在小宇宙收听」原生链接（`article.url` 永久有效，CDN 签名过期也不怕）。

**两个设计决策**（部署前知悉）：

- 写库失败**仅告警不阻断**：job 照常走完并 ready，本地文件仍是完整备份；
- **不回填存量数据**：老文章相关 tab 若 404 属预期，页面「重新解析」可触发 worker 重跑补齐。

## 2. 部署顺序（关键约束）

```
① push 两仓库
        │
② 云端 git pull + 重启 backend ──► backend 启动时 init_db 自动执行 022 迁移
        │                            （无需手动 psql；migrations/*.sql 幂等）
③ 验证三列已加 ──────────────► ⚠️ 必须在重启 worker 之前确认，
        │                        worker 写库依赖新列存在
④ 重启本地 worker（写库逻辑生效）
        │
⑤ 端到端验证（投递一条小宇宙链接）
```

> 顺序约束只有一条硬性的：**迁移（②③）先于 worker 重启（④）**。
> backend 与 worker 谁先谁后不影响正确性——先上 worker 时旧 backend 读不到新字段，表现与现状相同，无害。

## 8. 排障速查

| 现象 | 排查 |
| --- | --- |
| job ready 但相关 tab 404 | worker 写库被跳过：`grep "写库失败" 06-log/$(date +%F).log`（两条文案：`parse 结果写库失败（不阻断…）` / `转录/精读 HTML 写库失败（不阻断…）`），看具体异常——常见为 DB 连接中断 / 列未加（回步骤五） |
| 三列验证不足 3 行 | 022 未执行：查 `04-log/backend/$(date +%F).log` 中 `Migration warning (022_...)`；也可手动补跑 `docker exec -i inflow-db psql -U inflow -d inflow < 03-src/backend/core/migrations/022_articles_content_fields.sql` |
| 老文章 tab 404 | **预期内**（本次不回填存量）。需要数据时在页面点「重新解析」：云端重置状态 → worker 认领重跑 → 全字段按新逻辑直写补齐 |
| 音频播放失败 | 看页面是否自动出现「在小宇宙收听」按钮；出现即降级逻辑生效（CDN 签名过期），点按钮经 `article.url` 跳原平台 |
| worker 重启后不认领 | `tail -F 06-log/$(date +%F).log` 看自检节；确认 `.env.local-worker` 的 `DATABASE_URL` 指向云端 5432 且安全组白名单未变 |

## 10. 已知边界（验收时不要误判为 bug）

1. **存量老文章**（本次上线前经 worker 管线产出、ext=t 的）相关 tab 404 属预期——按决策忽略回填，「重新解析」可补；
2. **`media_url` 是平台签名 CDN 链接**，会过期——前端 `onError` 自动降级原平台收听按钮，属设计行为而非故障；
3. **图文类文章**没有 `transcript / media_url`，对应 tab 不可用属正常；
4. **写库失败不阻断**：极端情况下 job 照常 ready 而 tab 空——按排障表第 1 条定位，本地 `04-output/` 文件仍是完整数据源。

## 11. 实战回填（2026-08-30 上线当晚实际踩坑）

### 11.1 微信推送 failed「Card PNG not uploaded」→ 已修（`05cf1d7`）

**现象**：worker 日志显示 PNG 已 SFTP 回传云端
（`/www/data/inflow/pipeline/03_display/wechat/.../{job}.png`，文件确实在），
但 `wechat_callback_queue` 反复 failed `Card PNG not uploaded`，微信收不到卡片。

**根因**：`raw_file_path` 登记形态随管线代际不同。旧云端管线登记**云端绝对路径**
（bot 用 `display_card_png_path` 换段即命中）；本地 worker 登记 `04-output/01_ingest/...`
**相对形态**，bot 换段后在进程 cwd 下找 PNG 必然落空。worker 回传侧剥前缀拼
`SFTP_PIPELINE_DIR` 落盘正确，两侧寻径不同源——文件落对了位置，bot 却按旧形态找。

**修复**：conventions 新增 `card_png_candidates`（换段原样 + 剥 `data/`/`04-output/`
前缀拼 `INFLOW_PIPELINE_DATA_DIR` 双候选，按序 stat 取首个非空）；bot 推送与
deep-read 截图接口均改用。**前置配置**：云端 `.env` 必须有
`INFLOW_PIPELINE_DATA_DIR=/www/data/inflow/pipeline`（与 worker `SFTP_PIPELINE_DIR` 一致）。

**重推方法**（DB 直改，bot 5s 轮询自动认领）：

```sql
UPDATE wechat_callback_queue SET status='ready', error=NULL
WHERE job_id='<uuid>' AND status='failed';
```

> 排障提示：`03_display/wechat/...` 目录名里的 `wechat` 是**文章平台**（公众号），
> 与「是否从微信投递」无关；只有微信投的任务才有 queue 行。queue 里
> `pending`=worker 未翻 / `ready` 停留=bot 未跑 / `failed`=寻径或发送失败（error 列有详情）。

### 11.2 `column articles.transcript does not exist`（已自愈）

迁移执行**前**若云端已跑新代码（模型含 `transcript` 列），任何 ORM 全列查询
（含 bot 推送路径里的 `db.get(Article)`）都会炸 `UndefinedColumnError`。
本次为窗口期旧错误，`init_db` 补跑 022 后自愈。**教训：`git pull` 后立即重启**
（重启即触发迁移），不要 pull 完隔很久才重启。

### 11.3 双 bot 进程抢认领（已杀旧进程）

**现象**：8aa7ff0c（小宇宙）queue 第一次 failed 报**旧文案**
（`Card PNG not uploaded`，`05cf1d7` 后应为 `Card PNG not found ... tried [...]`），
而同晚另一条 job 正常 `sent`——新旧代码「随机」生效。

**根因**：服务器上有**两个** wechat-bot 进程并存——8/26 手动起的旧进程
（PID 3346420）从未退出，与新部署的（8/30，PID 1256599）竞争认领
queue 行（认领是原子 UPDATE，谁抢到谁处理，文案随进程版本）。4 天里
旧进程一直用旧寻径逻辑制造间歇性 failed。

**识别**：`ps -ef | grep "python -m backend.plugins.wechat.bot" | grep -v grep`
出现两行；旧进程启动日期早于最近部署即残留。**处置**：`kill <旧PID>`。
**预防**：每次部署重启后顺手跑一遍上面的 ps 确认只余一个；
start-server.sh 的重启只管自己 PID 文件里的进程，管不了手动起的历史进程。

### 11.4 环境坑（非本方案引入）

- 本机 `~/.ssh/id_ed25519` 曾于 08-26 19:35 重新生成而未登记 GitHub，
  导致 push 全部 `Permission denied (publickey)`——已在 GitHub 登记新公钥修复；
- 本机对服务器无免密 SSH（root 密码只在用户手里），服务器侧操作走
  腾讯云控制台网页终端 / 宝塔面板；云端 DB 可从本机 psql 直连（5432 白名单）；
- worker SFTP 偶发 `rc=255 Connection closed by remote host`（瞬时断连），
  断点续跑自愈重传成功——偶发可忽略，频繁复现再查宝塔 SSH 防爆破误封。
