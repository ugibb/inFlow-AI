## 一、产品重新定位

### 原项目定位

> 面向中文互联网的「稍后阅读 + AI 知识库」——终点是「读完、记住」

### 二次开发目标定位

> 以个人知识积累为基础、以 AI 辅助内容生产为核心的「第二大脑」——终点是「写出来、发出去」

### 核心价值链

```
采集（多场景、一键式）
  ↓  [RawCapture 标准文件落盘]
解析（多模态 → 结构化知识单元 + 语义向量）
  ↓  [ParsedContent 结构化文件 + Wiki 索引]
展示（模板渲染 → 用户可读视图）
  ↓  ← Phase 1 完成
创作（意图 + 知识召唤 → AI 初稿 → 人机协作编辑美化）
  ↓  [草稿定稿]
发布（一键对接发布平台）← Phase 2
```

### MVP 阶段划分


| 阶段          | 步骤           | 核心交付     |
| ----------- | ------------ | -------- |
| **Phase 1** | 采集 → 解析 → 展示 | 能收、能读、能搜 |
| **Phase 2** | 创作 → 定稿 → 发布 | 能写、能发    |

## 二、Pipeline 解耦核心设计原则

### 步骤间通信方式

**不用直接函数调用，用文件 + 状态事件驱动：**

```
Step 1 采集              Step 2 解析              Step 3 展示
─────────────         ─────────────────        ─────────────
触发 →                监听 captured 事件 →      监听 parsed 事件 →
  Adapter 抓取           读取 raw 文件             读取 parsed 文件
  序列化为                选平台模板                  写入 articles 表
  RawCapture JSON         调 LLM 解析                推进 stage=ready
  落盘到指定路径           生成 ParsedContent
                          建 Wiki 索引
ingest_jobs              ingest_jobs               ingest_jobs
  status=captured   →      status=parsed     →       status=ready
```

**三个关键决策：**

1. **步骤间用文件通信** — 每步骤只认识自己的输入文件，不关心上一步怎么产生的
2. **采集层用适配器模式** — 每个平台一个 Adapter，接口统一，互不影响，独立维护
3. **解析层用模板模式** — 每个平台一套 LLM Prompt 模板，标准化输出结构

## 三、各步骤输入输出规格

### Step 1：采集（Ingest）

**职责边界：只负责"拿到原始数据并落盘"，不做任何内容理解，不调 LLM**


| 项        | 规格                                               |
| -------- | ------------------------------------------------ |
| **触发方式** | URL 粘贴 / 文件上传 / 微信 Bot 转发 / 浏览器插件 / 正文粘贴         |
| **输入**   | 原始 URL 或文件或文本                                    |
| **处理**   | Platform 识别 → 对应 Adapter 抓取 → 序列化为标准格式           |
| **输出**   | `data/01_ingest/{platform}/{YYYYMMDD}/{index}-{title}/` 下：`{uuid}.json`（RawCapture）、`{uuid}.m4a` 等原始媒体文件（如有） |
| **完成信号** | `ingest_jobs.status = captured`（附 raw_file_path） |
| **不做什么** | 不调 LLM、不做 Markdown 转换、不写 articles 表              |


**RawCapture 标准格式（所有平台统一输出此格式）：**

```json
{
  "meta": {
    "id": "uuid",
    "source_platform": "wechat | bilibili | xiaoyuzhou | xhs | douyin | ...",
    "capture_method": "url | wechat_bot | browser_ext | upload | paste",
    "original_url": "https://...",
    "captured_at": "2026-06-18T10:00:00Z",
    "adapter_version": "1.0.0",
    "user_id": "uuid"
  },
  "raw": {
    "title": "原始标题（平台自带，未经 AI 处理）",
    "author": "作者",
    "published_at": "2026-06-01T00:00:00Z",
    "content_type": "article | video | audio | image | document",
    "raw_html": "...",
    "raw_text": "...",
    "media_urls": ["https://..."],
    "cover_image": "https://...",
    "extra": {}
  },
  "status": "captured"
}
```

---

### Step 2：解析（Parse）

**职责边界：读取 Step 1 文件，调 LLM，产出结构化数据 + 建 Wiki 索引**


| 项        | 规格                                                       |
| -------- | -------------------------------------------------------- |
| **触发方式** | 监听 `ingest_jobs.status = captured`（BackgroundTask）       |
| **输入**   | 从 `ingest_jobs` 读取 `raw_file_path` → 加载 RawCapture JSON  |
| **处理**   | 选平台模板 → 调 LLM → 产出结构化数据 → 向量嵌入 → 知识图谱边                   |
| **输出 1** | `data/02_parse/{platform}/{YYYYMMDD}/{index}-{title}/` 下：`{uuid}.json`（ParsedContent）、`{uuid}_asr.txt/.json/_verbose.json`（转录，如有） |
| **输出 2** | DB：`articles` 表预写入基础字段（`processing_stage = indexing`）    |
| **完成信号** | `ingest_jobs.status = parsed`（附 parsed_file_path）        |
| **不做什么** | 不渲染前端视图，不做最终 DB 记录写入                                     |


**ParsedContent 标准格式：**

```json
{
  "id": "uuid",
  "raw_file": "data/01_ingest/wechat/20260618/001-AI的边界与人类创造力/uuid.json",
  "parsed_at": "2026-06-18T10:05:00Z",
  "template_used": "wechat_article_v1",
  "article": {
    "title": "AI 解析后的标题",
    "summary": "5 句话摘要",
    "key_points": ["要点1", "要点2", "要点3"],
    "tags": ["标签1", "标签2"],
    "author": "作者名",
    "clean_content": "Markdown 正文...",
    "reading_time": 5,
    "word_count": 1200
  },
  "ai_meta": {
    "model": "deepseek-chat",
    "tokens_used": 1400,
    "template_version": "1.0"
  },
  "status": "parsed"
}
```

---

### Step 3：展示（Display）

**职责边界：读取 Step 2 结构化文件，写入 DB，提供前端可读视图**


| 项        | 规格                                                            |
| -------- | ------------------------------------------------------------- |
| **触发方式** | 监听 `ingest_jobs.status = parsed`（BackgroundTask）              |
| **输入**   | 从 `ingest_jobs` 读取 `parsed_file_path` → 加载 ParsedContent JSON |
| **处理**   | ParsedContent → `articles` 表完整写入 + embedding 写入               |
| **输出**   | DB `articles` 记录完整可读，`processing_stage = ready`               |
| **完成信号** | `ingest_jobs.status = ready`                                  |


**Phase 1 到此完成。**

---

### Step 4：创作（Compose）— Phase 2


| 项        | 规格                                                                  |
| -------- | ------------------------------------------------------------------- |
| **触发方式** | 用户主动：填写意图 + 读者 + 思路，点击生成                                            |
| **输入**   | `{ intent, audience, outline }` + 用户知识库向量检索（articles + annotations） |
| **处理**   | 知识召唤 → Prompt 构建 → LLM SSE 流式生成初稿                                   |
| **输出**   | `drafts` 表记录（含 `source_citations`）+ 载入编辑器                           |


### Step 5：发布（Publish）— Phase 2


| 项        | 规格                                 |
| -------- | ---------------------------------- |
| **触发方式** | 用户主动：草稿定稿后点击发布                     |
| **输入**   | `drafts.content`（Markdown）+ 目标平台选择 |
| **处理**   | 发布 Adapter 转换格式 → 调用目标平台 API       |
| **输出**   | 发布记录 + 返回发布 URL                    |

## 四、采集层适配器设计

### AbstractAdapter 接口

```python
class AbstractAdapter:
    platform: str       # 平台唯一标识（wechat / bilibili / xiaoyuzhou ...）
    version: str        # Adapter 版本号，平台改版时递增

    def can_handle(self, url: str) -> bool
    # 判断此 Adapter 能否处理该 URL（用于自动路由）

    async def fetch(self, url: str) -> RawCapture
    # 核心方法：抓取并返回 RawCapture 标准对象

    def get_parse_template_id(self) -> str
    # 返回此平台对应的解析模板 ID
```

### 各平台核心挑战


| 平台        | 内容类型            | 核心技术挑战                  |
| --------- | --------------- | ----------------------- |
| 微信公众号     | 图文              | Playwright 渲染 + 防盗链图片代理 |
| 小宇宙       | 音频（播客）          | 音频流 URL 提取 → ASR 转录     |
| B站        | 视频              | 字幕/ASR 提取 + 评论          |
| 小红书       | 图文/视频           | TLS 指纹绕过 + 登录态          |
| 抖音        | 视频              | 视频流提取 → ASR             |
| YouTube   | 视频/音频           | yt-dlp 下载 → Whisper 转录  |
| 头条        | 图文              | 动态渲染（Playwright）        |
| 掘金 / CSDN | 图文              | 标准 HTTP，较简单             |
| 通用网页      | 图文              | OpenGraph 解析兜底          |
| 文件上传      | PDF/DOCX/EPUB 等 | MarkItDown 转换           |


### 解析模板（Parse Templates）

每个平台对应一套 LLM Prompt 模板，规范输出 ParsedContent：

```python
class AbstractTemplate:
    template_id: str       # 模板唯一标识
    platform: str          # 对应平台
    version: str           # 模板版本

    def build_prompt(self, raw: RawCapture) -> str
    # 构建平台专属的 LLM 解析 Prompt

    def parse_response(self, llm_output: str) -> ParsedArticle
    # 解析 LLM 输出为结构化数据
```

## 六、代码文件目录规划

### 命名规则说明

> **Python 模块名约束**：目录名以数字开头（如 `01-ingest`）或含连字符均无法被 Python `import`。
> 本方案采用 **方案 B**：业务流水线目录统一以 `s{N}_` 前缀命名（如 `s1_ingest`），
> 兼顾文件系统自然排序与 Python 合法标识符两个要求。

## 九、技术风险与应对


| 风险                   | 说明                                    | 应对策略                                                                              |
| -------------------- | ------------------------------------- | --------------------------------------------------------------------------------- |
| 平台反爬变动               | 微信/小红书等平台频繁更新反爬策略                     | Adapter 版本化（`adapter_version`），旧版 raw 文件保留，重采集只改 Adapter                          |
| ASR 转录延迟             | 小宇宙/B站音视频转录耗时长                        | 采集层返回 `content_type=audio/video` 后，ASR 异步处理，RawCapture 先落盘，转录完成后补填 `raw_text`     |
| LLM 解析模板漂移           | LLM 输出格式不稳定，Template 解析失败             | `parse_response()` 内置 JSON 修复（复用 `ai_service.robust_json_parse`），失败降级为 generic 模板 |
| 文件存储膨胀               | raw/parsed 文件长期累积                     | `storage/conventions.py` 定义归档策略；后期可扩展 S3/OSS 实现                                   |
| 过渡期双轨并行              | `parser_service.py` 与新 `ingest/` 同时存在 | 新路由走新链路，旧路由保留不动，逐步迁移，迁移完成后删除旧 service                                             |
| BackgroundTask 进程内丢失 | 服务重启时未完成任务丢失                          | `ingest_jobs` 表记录状态，重启后扫描 `status IN (capturing, parsing, displaying)` 的记录重新触发    |

## 十二、代码结构重构执行计划（v1.3 新增）

### 背景

现有 `03-src/backend/app/` 存在以下问题：
1. `01-ingest/`、`02-parse/`、`03-services/`、`04-storage/` 目录名含数字前缀和连字符，**Python 无法 import**，应用当前无法正常启动
2. `03-services/` 将 AI 服务、音频处理、图谱、研究 Agent、Obsidian 写入等完全不同职责的模块混放，耦合严重
3. `routers/` 下 11 个路由文件扁平堆放，`articles.py` 高达 1127 行，业务边界模糊

### 目标

重构后每个业务步骤自成一包，依赖关系单向（低编号步骤不依赖高编号）：

```text
core/ ← shared/ ← pipeline/ ← s1_ingest ← s2_parse ← s3_display ← s4_compose ← s5_publish
                                    ↑           ↑           ↑
                               extensions/  extensions/  extensions/
```
