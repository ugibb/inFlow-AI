# 本地独立 Worker 承接 inFlow 完整 Pipeline 重构方案

- 日期：2026-08-19
- 状态：待实施（分 4 阶段）
- 范围：URL 内容采集 → 转录 → chapters → parse → compose → index 全链路外部化到本地
- 相关系统：inFlow backend / wechat-bot / frontend / PostgreSQL（云端）、local_worker（本地 Mac）

---

## 一、背景与动机

inFlow AI 部署在腾讯云（大陆 IP），无法访问 Groq ASR API（403 Forbidden）。现有兜底「本地 faster-whisper」在服务器上既无模型路径也无 CPU 算力；通义听悟成本高；SiliconFlow 有单请求 ≤1 小时限制。

**根本矛盾**：转录等重计算需要访问国外 AI 服务，而腾讯云生产环境访问不了外网 AI。

**目标**：把 inFlow 完整 pipeline（采集→转录→chapters→parse→compose→index）迁移到**本地独立 worker**。本地能访问外网、可自由选择 ASR。腾讯云只保留入口/存储/展示/推送。本地 worker **直连云端 PostgreSQL**（5432 白名单）作为任务总线。

### 已确认的决策（多轮讨论定稿）

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 承接边界 | 采集 + 转录 + 后续全部 pipeline **都本地**（不只音频） |
| 2 | 任务同步机制 | 本地 worker 直连云端 PostgreSQL 作为任务总线（复用 `IngestJob` 状态机） |
| 3 | 云端 PG 可达性 | 可直连，5432 开白名单（仅本地 IP / SSH 隧道） |
| 4 | 数据模型 | 接受给 `IngestJob` 增加字段（`external_processing` 等） |
| 5 | 分流标准 | **全部内容类型**（音频/图文/视频）都走本地 worker |
| 6 | 微信 bot | 只需同步任务（URL + job_id），不需同步媒体；bot 只调 `/api/ingest/url` |
| 7 | ASR 选择 | 本地自由选：Groq（主）/ SiliconFlow / faster-whisper（兜底） |
| 8 | 卡片 PNG 回传 | 本地 **SFTP 直传**云端 pipeline 目录，**不开 HTTP API**（复用 SSH 22，免明文 FTP） |

## 二、目标架构

```text
┌─ 云端 · 腾讯云 ──────────────────────────────────────────────┐
│  · 微信 bot：收 URL → POST /api/ingest/url（标记本地处理）      │
│  · backend：建 Article stub + IngestJob（external_processing）│
│          对本地处理的 job 不再跑 capture/pipeline             │
│  · PostgreSQL：5432 开白名单给本地                           │
│  · 前端：读 Article 表（DB），不碰文件                       │
│  · 微信 bot 推卡片：读云端磁盘 PNG（SFTP 直传落盘，无需新 API）│
└───────────────────────────────────────────────────────────┘
              ↓ 本地直连 PG（轮询 + FOR UPDATE SKIP LOCKED 原子认领）
┌─ 本地 · Mac ────────────────────────────────────────────────┐
│  inFlow local_worker（复用 backend 全部代码）                │
│  · 轮询 external_processing 的待处理 job                    │
│  · 采集（本地抓 URL/下载媒体）→ 转录（Groq/SF/本地任选）       │
│  · chapters → parse → compose（Playwright 渲染 PNG）→ index  │
│  · parse 结果写回 Article 表 → 前端直接展示                  │
│  · 卡片 PNG 经 SFTP 直传云端 pipeline 目录 → bot 推送        │
│  · 全部文件在本地 data/，音频用完即弃，不回传                 │
└───────────────────────────────────────────────────────────┘
```

**核心不变量**：`raw_file_path` 存 DB 时始终是**相对路径** `data/01_ingest/{platform}/{date}/{folder}/{job_id}.json`（LocalStorage 已如此）。云端与本地 cwd 均为 backend 目录，`Path("data/03_display/...")` 两端正确解析——这是 PNG 回传成立的前提。

字段语义：

| 字段 | 语义 |
|------|------|

## 四、云端改动清单

### 1. `app/s1_ingest/orchestrator.py`

- **`ingest_url`**：job flush 后若 `settings.external_processing`（新增配置，**默认 False，opt-in**；云端必须显式 `EXTERNAL_PROCESSING=true` 才开启分流）→ 置 `job.external_processing=True`、commit、**跳过** `transition(pending→capturing)`、**跳过** `background_tasks.add_task(_run_url_capture)`，直接返回 job_id。`_peek_url_title` / `log_task_start` 照跑。默认 False 防止误开导致 worker 未部署时所有 URL 静默卡 pending；开启时 backend 启动会打 warning 提示确认 worker 已运行。
- **`resume_job`**：开头判断 `job.external_processing` → 直接 return（云端不调度，交给本地 worker）。
- **`recover_captured_jobs`**：SELECT 加 `.where(IngestJob.external_processing.is_(False))`。
- **`_route_pipeline` / `_run_resume`**：增加可选参数 `on_composed: Callable[[UUID, str], Awaitable[bool]] | None = None`。抽私有助手 `_compose_and_continue(...)` 收敛 5 处内联 compose+index；`run_compose_card` 成功后若 `on_composed` 存在则调用（返回 PNG 回传成败，失败则 transition composed→failed, error_stage="composing"），成功才继续 `run_index`。云端路径传 `None`，行为零变化。

### 2. `app/core/pipeline/pipeline_steps.py`（前端 PipelineBar 进度）

云端读不到本地文件，`_step_done` 按文件存在判定会全 pending。外部 job 改用**状态排名判定**：

```python
_EXT_RANK = {"pending":0,"capturing":1,"captured":2,
             "normalizing":3,"normalized":4,"transcribing":3,"transcribed":4,
             "parsing":5,"parsed":6,"composing":7,"composed":8,
             "indexing":9,"ready":10,"failed":0,"cancelled":0}
_EXT_STEP_DONE_RANK = {"capture":2,"media_download":2,"normalize":4,"transcribe":4,
                       "chapters":6,"parse":6,"compose_html":8,"compose_png":8,"index":10}
```

`compute_pipeline_steps` 中若 `job.external_processing`，用 `_EXT_RANK[job.status] >= _EXT_STEP_DONE_RANK[spec.id]` 覆盖 done_flags，其余装配逻辑复用。

### 3. PNG 回传：本地 SFTP/SCP 直传云端 pipeline 目录（无需新开 API）

本地 worker compose 出 PNG 后，经 **SFTP（复用 SSH 22 端口）** 直传云端 `$INFLOW_PIPELINE_DATA_DIR` 对应目录，**云端不新增任何端点**：

```bash
# 本地 worker 侧（subprocess 调 sftp，或 paramiko）
src="${PNG_LOCAL_PATH}"                                       # 本地 data/03_display/.../{job_id}.png
rel=$(ext_display_card_png_rel "$RAW_FILE_PATH" "$JOB_ID")    # 03_display/{platform}/{date}/{folder}/{job_id}.png
sftp -b - "inFlow_worker@${SFTP_HOST}" <<EOF
  mkdir -p "${SFTP_PIPELINE_DIR}/$(dirname "$rel")"
  put "${src}" "${SFTP_PIPELINE_DIR}/${rel}.tmp"
  rename "${SFTP_PIPELINE_DIR}/${rel}.tmp" "${SFTP_PIPELINE_DIR}/${rel}"
EOF
```

要点：

- **通道**：走 SFTP/SCP 复用 SSH 22（运维端口已通），**不用明文 FTP 21**；本地 Mac 的 `~/.ssh/id_ed25519.pub` 加入云端 `authorized_keys` 即鉴权，无需新建 FTP 账号
- **路径一致性**：本地必须知道云端 `SFTP_PIPELINE_DIR`（与云端 `INFLOW_PIPELINE_DATA_DIR` 一致，写入 `.env.local-worker`）；目标相对路径由 `conventions.display_card_png_path(raw_file_path, job_id)`（`data/03_display/...`）剥 `data/` 前缀得到，与 bot 读取路径同源
- **原子落盘**：先传 `{job_id}.png.tmp` 再 `rename`，避免 bot 读到半文件
- **时序不变**：compose 之后、index 之前同步上传；失败返回 False → job 停 `composing failed`

### 4. `app/core/shared/storage/conventions.py` 新增

```python
def ext_display_card_png_rel(raw_file_path: str, job_id: UUID) -> str:
    """本地 worker 回传 PNG 的云端相对路径（相对 $INFLOW_PIPELINE_DATA_DIR）。"""
    return display_card_png_path(raw_file_path, job_id).removeprefix("data/")
```

### 5. `app/extensions/wechat/bot.py`（推卡守卫）

`_process_ready_callbacks` 中 PNG 缺失时补渲染 fallback：若 `job.external_processing` → 直接 raise（PNG 未回传），不再本地补渲染（云端无文件必炸）。

## 五、本地 worker 设计（分层解耦）

> 关键前提：**渠道采集已通过 `AbstractAdapter` 接口与核心逻辑解耦**（`app/s1_ingest/adapters/base.py` 明确约定 adapter 只产出 `RawCapture`，禁止调 LLM / 写 DB / 做 Markdown 转换 / 碰 articles 表）。本方案直接复用这套现有体系，无需重写。

### 5.1 四层解耦架构

| 层 | 组件 | 职责 | 解耦边界 |
|----|------|------|----------|
| L1 渠道采集层 | `app/s1_ingest/adapters/`（11 个 adapter + `registry.py`） | URL → `RawCapture` | 纯函数式；不碰 DB/LLM；新增渠道不改 worker/pipeline/DB |
| L2 任务调度层 | `app/local_worker/`（新进程） | 认领 / 租约 / 心跳 / 断点续跑 | 只做调度，不含业务逻辑 |
| L3 核心处理层 | `s2_parse` / `s3_display` / `s4_compose` / `core/pipeline/steps.py` | 转录 / parse / compose / index | 消费 `RawCapture`；ASR 走 provider 工厂可替换 |
| L4 同步回传层 | PG 直写 + SFTP PNG 回传 | Article / step_logs 入库、PNG 落云端 | 与 inFlow 前端仅通过 DB 交互 |

### 5.2 渠道抓取如何工作（本地 worker 与云端同源）

worker 认领 job 后，渠道抓取走与云端 `_run_url_capture`（`orchestrator.py:443`）**完全相同的代码路径**：

```python
# worker 内（由 _run_resume 的 captured 分支触发，复用云端逻辑）
adapter = adapter_registry.resolve(job.source_url)        # 按 URL 选渠道（wechat/xiaoyuzhou/…）
raw_capture = await adapter.fetch(                        # 纯采集，产 RawCapture
    url=job.source_url, user_id=job.user_id,
    capture_method=job.capture_method or "url")
raw_path = await default_storage.write_raw(               # 写本地 data/01_ingest/{platform}/{date}/{folder}/{job_id}.json
    platform=adapter.platform, job_id=job.id,
    data=raw_capture.to_dict())
await _download_media_if_needed(raw_capture, raw_path, job.id, phase=phase)  # 音频/视频下载到本地
await transition(db, job.id, "capturing", "captured", raw_file_path=raw_path)
await _route_pipeline(...)                                # 按 content_type 路由后续
```

要点：

- **路由靠 `adapter_registry.resolve(url)`**：`can_handle()` 是快速正则/域名匹配（无网络 I/O），11 个渠道已注册（wechat / bilibili / xiaoyuzhou / xhs / douyin / youtube / toutiao / juejin / csdn / feishu + generic 兜底）
- **本地 vs 云端唯一区别是运行环境**：本地可访问外网（Groq、各平台），云端不能——这正是 worker 存在的意义
- **断点续跑**：`_run_resume` 的 pending/capturing 分支会自动重走 `adapter.fetch`（崩溃在采集中途 → 回退 pending 重采）

### 5.3 「独立服务」的两种形态

- **形态 A（本方案落地）——单 worker 进程内按渠道路由**：渠道 adapter 常驻同一进程，`registry` 统一路由。部署仅一个进程，渠道共享 worker 的 PG/SFTP 通道；渠道仍是独立模块（独立文件、独立测试、独立 `adapter.version`），满足「新增渠道不碰核心」。
- **形态 B（未来可选）——渠道采集器独立部署**：把某渠道 adapter 包装为独立可运行服务（CLI `python -m app.channels.xiaoyuzhou --url …` 或 HTTP），worker 改为调用该服务取 `RawCapture`。`AbstractAdapter` 就是现成契约，届时把 adapter 抽到独立包即可，worker/pipeline/DB 零改动。

### 5.4 功能服务解耦边界（可独立替换 / 独立部署）

| 功能 | 组件 | 本地 worker 的选择 |
|------|------|-------------------|
| ASR 转录 | `build_transcriber()` 工厂（`s2_parse/audio/transcriber_factory.py`） | 本地按 `ASR_PROVIDER` 自由切换 groq / tingwu / siliconflow / faster-whisper |
| 精华卡渲染 | `card_renderer.py`（Playwright） | 本地 `python -m playwright install chromium` |
| 文件存储 | `AbstractStorage` / `LocalStorage`（`core/shared/storage`） | 全部走 storage 接口，渠道/处理层不直接碰文件系统 |
| 语义索引 | `wiki_indexer.py`（SiliconFlow embedding） | 本地直连 SF embedding API |

### 5.7 主循环

```python
async def main():
    await reclaim_own_host()          # 清理本机遗留租约
    while True:
        job = await claim_next_job()
        if job is None:
            await asyncio.sleep(SCAN_INTERVAL_S); continue
        heartbeat = asyncio.create_task(_heartbeat(job.id))
        try:
            await process_job(job.id)
        except Exception:
            logger.exception("job %s 处理异常", job.id); await _mark_failed_guarded(job.id)
        finally:
            heartbeat.cancel(); await release_lease(job.id)
```

### 5.8 认领（防多实例并发）

```python
_CLAIMABLE = ("pending","capturing","captured","normalizing","normalized",
              "transcribing","transcribed","parsing","parsed","composing","composed","indexing")
stmt = (select(IngestJob)
    .where(IngestJob.external_processing.is_(True),
           IngestJob.status.in_(_CLAIMABLE),
           IngestJob.article_id.isnot(None),
           or_(IngestJob.claimed_at.is_(None),
               IngestJob.claimed_at < now_utc() - timedelta(seconds=LEASE_SECONDS)))
    .order_by(IngestJob.created_at.asc()).limit(1)
    .with_for_update(skip_locked=True))      # 与 review_cron_loop 同款
```

认领后置 `processing_host=WORKER_HOST`、`claimed_at=now`。**推荐单 worker**：多 worker 时 `article_folder_name` 的 `len(existing)+1` 序号推导有跨进程竞态（需 DB 序列才可放开）。

### 5.9 心跳（长任务防被抢，解决听悟 ASR 数小时问题）

每 120s `UPDATE ingest_jobs SET claimed_at=now()`。

### 5.10 每 job 处理（复用 `_run_resume` 断点续跑）

```python
async def process_job(job_id):
    async with async_session() as db:
        job = await db.get(IngestJob, job_id)
        if job and job.status == "capturing":      # 崩溃在采集中途 → 回退重采
            await _force_set_status(db, job_id, "pending")
    await _run_resume(job_id=job_id, on_composed=_upload_card_png_via_sftp)
```

`_run_resume` 各分支已实现 pending→capturing→captured→_route_pipeline，以及各中间态断点续跑，无需重写 pipeline 序列。

### 5.10.1 并发安全加固（代码审查后追加，worker 多写入者）

worker 引入第二个写入者后，原云端单写入者假设不再成立。审查（20260820）修复：

1. **`transition()` 原子化（CAS）**：`UPDATE ... WHERE id=:job_id AND status=:current_status`，`rowcount==0` 时 rollback 并抛 `RuntimeError`。租约超时被抢后，过期 owner 的 transition 安全失败，不再回退/覆盖新 owner 进度。云端单写入者路径 `rowcount` 恒为 1，行为零变化。
2. **所有权守卫**：`release_lease` / `_heartbeat` / `mark_failed_guarded` 的 UPDATE 均加 `processing_host == worker_settings.worker_host`；`_heartbeat` 在 `rowcount==0`（已失主）时停止续租。被抢占的旧 worker 不再能清空新 owner 的 `claimed_at` 或改写 job。
3. **`mark_failed_guarded` 走状态机**：非终态 + 本机 owner 时用 `transition(→failed, error_stage="worker")`，不再裸 UPDATE 绕过状态机。
4. **`reclaim_own_host` 前缀匹配**：`processing_host` 含 PID（重启变化），按 `hostname-%` 前缀回收本机遗留租约，而非精确相等。
5. **composed 分支补回传**：崩溃于 compose 之后、SFTP 回传完成前时，`_run_resume` 的 `composed` 分支重跑 `on_composed`（`.tmp→rename` 幂等覆盖），失败则停 `composed→failed`，杜绝「ready 却无云端 PNG」。
6. **SFTP 120s 超时**：`asyncio.wait_for(communicate(...), timeout=120)`，网络黑洞不卡死整个串行 worker。

## 七、风险与对策

| # | 风险 | 对策 |
|---|------|------|
| 1 | PNG 路径一致性 | 本地用 `display_card_png_path` 剥 `data/` 前缀 + `SFTP_PIPELINE_DIR` 拼目标，两端配置一致；bot 外部 job 禁用补渲染 |
| 2 | Playwright 本地依赖 | `python -m playwright install chromium`；start-worker.sh 前置检查（playwright/ffmpeg） |
| 3 | worker 并发防抢 | `FOR UPDATE SKIP LOCKED` + claimed_at 租约 + 心跳；默认单进程 |
| 4 | 云端重启恢复抢外部 job | `recover_captured_jobs` 排除 external_processing |
| 5 | 前端进度可见性 | `compute_pipeline_steps` 状态排名判定；`append_step_log` 跨进程实时可用 |
| 6 | `auto_backfill_embeddings` 给 in-flight stub embedding | 索引后覆盖，低危害；可加 `skip if fetch_status=='ingesting'` |
| 7 | 长 ASR 超租约被抢 | `_heartbeat` 每 120s 刷新 claimed_at |
| 8 | upload/paste 留云端处理 | 本轮范围：URL ingest 全外部化；upload/paste 后续再做 |
| 9 | SFTP 凭据与权限 | 仅本地 Mac 公钥授权；`03_display` 子目录最小写权限；不用明文 FTP |
| 10 | 5432 暴露公网 | 安全组仅放行本地 IP；备选 SSH 隧道 |
