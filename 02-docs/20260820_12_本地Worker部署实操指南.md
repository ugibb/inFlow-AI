## 0. 开始前：你需要确认的东西


| 项                      | 值                                                                     | 在哪确认                                                    |
| ---------------------- | --------------------------------------------------------------------- | ------------------------------------------------------- |
| 云端仓库路径                 | `/www/wwwroot/<站点>`（宝塔）                                               | 服务器 `pwd`                                               |
| 云端公网 IP                | 腾讯云控制台 → 实例                                                           | 控制台                                                     |
| 云端 Postgres 密码         | `.env` 的 `POSTGRES_PASSWORD`                                          | 服务器 `grep POSTGRES_PASSWORD .env`                       |
| 云端 pipeline 目录         | `.env` 的 `INFLOW_PIPELINE_DATA_DIR`，生产宝塔为 `/www/data/inflow/pipeline` | 服务器 `grep INFLOW_PIPELINE_DATA_DIR .env`                |
| 本地 Mac 公网 IP           | 搜索「我的IP」                                                              | 腾讯云安全组放行用                                               |
| 本地 Mac SSH 公钥          | `~/.ssh/id_ed25519.pub`                                               | `cat ~/.ssh/id_ed25519.pub`（无则 `ssh-keygen -t ed25519`） |
| Groq / SiliconFlow Key | 各控制台                                                                  | 填进本地 `.env.local-worker`                                |


**安全红线（全程不可破）**：

1. 腾讯云安全组 5432 只放行**本地 Mac 公网 IP**，绝不 `0.0.0.0/0`。
2. SFTP 只走**本地 Mac 公钥授权** + 最小 `03_display` 子目录写权限，不开明文 FTP 21。
3. 密钥只进 `.env` / `.env.local-worker`（已 gitignore），不写进代码/文档。

## 2. 云端部署（腾讯云服务器执行）

> 部署形态：**直接代码部署**——保留 postgres / redis / nginx / frontend 容器作为基础设施，
> backend 与 wechat-bot 直接跑在宿主机（`uvicorn inflow_server.main:app` / `python -m inflow_server.extensions.wechat.bot`），
> 日志写 `04-log/backend`、`04-log/wechat-bot` 文本文件，PID 管理在 `.server/`。
> 改代码 `git pull` 后跑一次 `./deploy/cloud/start-server.sh --restart` 即生效；问题定位直接 `tail` 文本日志，不用再翻 `docker logs`。



### 2.1 拉代码 + 装后端依赖（一次性）

```bash
cd /www/wwwroot/<站点>
git pull

# backend 直接跑宿主机，首次需建 venv 并装依赖（不再依赖 backend 容器镜像）
# requirements 首行 `-e ../core` 会同时安装共享引擎 inflow-core
cd 03-src/server
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

预期：拉取上述文件；若本地 Git 与云端不同步，先解决冲突再继续。

### 2.2 打开分流开关（⚠️ 关键，漏了等于没部署）

默认是 `false`。**必须显式开启**，否则云端会继续自己跑 pipeline（腾讯云访问不了 Groq → 403）。

```bash
cd /www/wwwroot/<站点>
grep -q '^EXTERNAL_PROCESSING=' .env \
  && sed -i 's|^EXTERNAL_PROCESSING=.*|EXTERNAL_PROCESSING=true|' .env \
  || echo 'EXTERNAL_PROCESSING=true' >> .env

# 确认
grep '^EXTERNAL_PROCESSING=' .env
```

预期输出：`EXTERNAL_PROCESSING=true`

> 若你暂时不想上 worker（先让云端继续自己处理），这步改为 `false` 或跳过。但那样 **ASR 仍是 403**，不是最终目标态。



### 2.3 首次启动：拉起基础设施容器 + 直跑 backend/bot

```bash
cd /www/wwwroot/<站点>
./deploy/cloud/start-server.sh --detach
```

`start-server.sh` 会自动：① 补齐 `.env`（生成 `POSTGRES_PASSWORD` / `SECRET_KEY` / `SERVICE_TOKEN_WECHAT_BOT`）；② 拉起基础设施容器（postgres / redis / nginx / frontend）；③ 直跑 backend（`uvicorn inflow_server.main:app --port 8000`，源码在 `03-src/server`）与 wechat-bot；④ 健康检查 `http://127.0.0.1:8080/api/health`。

预期：结尾打印 `inFlow AI 已运行（直接代码部署）`。

> ⚠️ 若机器首次构建 frontend 镜像，会慢几分钟，耐心等健康检查通过。
> 若报「未找到 backend venv」，先回 2.1 建 `.venv`。
> 启动时 `init_db()` 自动执行 `migrations/018_external_processing.sql`（幂等，可反复跑）。



### 2.4 验证迁移已生效

```bash
docker exec inflow-db psql -U inflow -d inflow -c "\d ingest_jobs" | grep -E "external_processing|processing_host|claimed_at"
docker exec inflow-db psql -U inflow -d inflow -c "\di idx_ingest_jobs_ext_status"
```

预期：3 个新列 + `idx_ingest_jobs_ext_status` 索引存在。

### 2.5 验证后端启动无异常

```bash
tail -f 04-log/backend/$(date +%F).log
```

预期：`inFlow AI started successfully`；若 `EXTERNAL_PROCESSING=true` 会看到一条 **warning**（提示确认本地 worker 已运行），这是正常的。

### 2.6 安全组放行 5432（腾讯云控制台，不是服务器命令）

1. 云服务器 CVM → 安全组 → 找到实例绑定的安全组 → 入站规则 → 添加规则；
2. **类型**：自定义 TCP；**来源**：`<本地Mac公网IP>/32`；**端口**：`5432`；**协议**：TCP；**策略**：允许。
3. 确认没有已有的 `0.0.0.0/0` 覆盖 5432（有就删掉）。

> ⚠️ 若云端防火墙/宝塔面板另有放行，需同步放行同一来源。



### 2.7 创建 SFTP 回传账号并授权

```bash
# ① 创建最小权限用户（无 shell、仅 SFTP 场景下也建议 nologin + 目录属主）
useradd -m -s /bin/bash inFlow_worker
mkdir -p /www/data/inflow/pipeline/03_display
chown -R inFlow_worker:inFlow_worker /www/data/inflow/pipeline

# ② 确认 SFTP_PIPELINE_DIR 与云端 pipeline 目录一致
grep '^INFLOW_PIPELINE_DATA_DIR=' .env
# 生产宝塔应为 /www/data/inflow/pipeline（若不同，2.9 本地 .env.local-worker 的 SFTP_PIPELINE_DIR 必须跟它一致）
```

**授权本地 Mac 公钥**（在 Mac 上执行）：

```bash
cat ~/.ssh/id_ed25519.pub    # 复制输出
```

然后到服务器：

```bash
mkdir -p /home/inFlow_worker/.ssh
echo '<粘贴 Mac 公钥内容>' >> /home/inFlow_worker/.ssh/authorized_keys
chmod 700 /home/inFlow_worker/.ssh
chmod 600 /home/inFlow_worker/.ssh/authorized_keys
chown -R inFlow_worker:inFlow_worker /home/inFlow_worker/.ssh
```

**可选收紧**：若用宝塔/SSH 管理方便，可只给 `inFlow_worker` 开 SFTP chroot 到 `/www/data/inflow/pipeline`（本文档不做强制，安全组已兜底）。

### 2.8 云端部署自检清单

```bash
docker exec inflow-db psql -U inflow -d inflow -c \
  "SELECT 1;"                                # ① DB 可连
docker exec inflow-db psql -U inflow -d inflow -c \
  "\d ingest_jobs" | grep external_processing  # ② 迁移列存在
grep '^EXTERNAL_PROCESSING=' .env              # ③ 分流开关 true
grep started 04-log/backend/$(date +%F).log | tail -1  # ④ 后端启动正常
curl -s http://127.0.0.1:8080/api/health       # ⑤ 反代链路（nginx→host backend:8000）通
```

全部通过 → 云端就绪。先不要急着提交 URL，等本地 worker 起好再端到端联调。

### 2.9 日常更新（拉代码 / 改 .env 后）

```bash
cd /www/wwwroot/<站点>
git pull
./deploy/cloud/start-server.sh --restart    # 重建 frontend 容器 + 重启直跑 backend/bot
```

- 只改 `.env` 不用拉代码：同样 `./deploy/cloud/start-server.sh --restart`（会自动重新加载环境变量）。
- 停止直跑应用（容器不动）：`./deploy/cloud/stop-server.sh`。
- 停止全部 infra 容器：`docker compose -f docker-compose.yml -f deploy/cloud/docker-compose.baota.yml down`。
- 只看日志：`./deploy/cloud/start-server.sh --logs`。

## 3. 本地部署（Mac 执行）



### 3.1 确认代码与依赖

```bash
cd <inFlow-ai仓库>/03-src/worker
source .venv/bin/activate            # 已有 venv 则直接用
pip install -r requirements.txt      # 确保依赖全
python -m playwright install chromium   # compose 渲染 PNG 需要
brew install ffmpeg                     # 音频转码/下载可能用到
```

检查关键命令存在：

```bash
command -v sftp && command -v ffmpeg && python -m playwright --version
```



### 3.2 写本地 worker 配置

```bash
cd <inFlow-ai仓库>
cp deploy/worker/.env.local-worker.example 03-src/worker/.env.local-worker
vim 03-src/worker/.env.local-worker
```

按注释填入：

```ini
# ── 云端 PostgreSQL（任务总线）──
DATABASE_URL=postgresql+asyncpg://inflow:<云端POSTGRES_PASSWORD>@<云端公网IP>:5432/inflow

# ── 本地 ASR（可自由选，推荐 groq）──
ASR_PROVIDER=groq
GROQ_API_KEY=<Groq Key>
SILICONFLOW_API_KEY=<SF Key>

# ── SFTP PNG 回传（必须与云端 INFLOW_PIPELINE_DATA_DIR 一致）──
SFTP_HOST=<云端公网IP>
SFTP_USER=inFlow_worker
SFTP_PORT=22
SFTP_PIPELINE_DIR=/www/data/inflow/pipeline
```

> 密码/Key 若含 `;`、`"`、弯引号等特殊字符：`start-worker.sh` 会用 python-dotenv 安全加载，**不要**在文件里自己加转义，按原文写即可。



### 3.3 验证网络连通

```bash
nc -vz <云端公网IP> 5432          # ① 安全组放行后应通
psql "postgresql://inflow:<云端密码>@<云端公网IP>:5432/inflow" -c "SELECT 1;"
# 若 psql 未装：brew install libpq 后用 /opt/homebrew/opt/libpq/bin/psql
```

预期：`SELECT 1` 返回 `1`，无权限错误。

### 3.4 启动 worker

```bash
cd <inFlow-ai仓库>
./deploy/worker/start-worker.sh            # 前台启动 + 跟踪日志（Ctrl+C 只退出跟踪，worker 继续后台）
```

日志路径：`04-log/worker/YYYY-MM-DD.log`。

预期启动日志：

```
[INFO] worker 已启动（PID xxxx）
worker 启动: host=MacBook-xxxx hostname... scan=10s lease=600s heartbeat=120s sftp=on
```

**如果你没配 SFTP_HOST / SFTP_PIPELINE_DIR**，会看到一条 warning「PNG 卡片将不回传云端」——这就是阶段 2 的空跑模式，联调时先确认 `sftp=on`。

停止：`./deploy/worker/stop-worker.sh`（或 `pkill -f 'inflow_worker'`）。

## 5. 故障排查



### F1：worker 连不上 5432

```bash
nc -vz <IP> 5432
```

- 不通 → 安全组是否放行本地 IP /32？宝塔或系统防火墙是否放行？
- 能通但连接超时 → 检查 postgres 容器端口（`docker compose port postgres 5432`）。



### F2：job 一直 pending，worker 无日志认领

- 云端 `.env` 是否 `EXTERNAL_PROCESSING=true`？`false` 时云端会自己处理（可能 403）；
- 查 `SELECT id,external_processing,status,claimed_at FROM ingest_jobs ORDER BY created_at DESC LIMIT 3;`
  - `external_processing=false` → 分流没开；
  - `claimed_at` 有新时间 → 已被别的主机认领/心跳在刷（可能是旧 worker 进程残留，`pkill -f inflow_worker` 后重启）。



### F3：worker 认领后本地报错

看 `04-log/worker/*.log` 里最近的 Traceback，常见：

- `ModuleNotFoundError` → `pip install -r requirements.txt`；
- Playwright 渲染失败 → `python -m playwright install chromium`；
- 转录 403 → 本地访问 Groq 应正常；若被墙确认网络出口。



### F4：PNG 没回传，job 停在 `composing failed` / `error_stage=composing`

```bash
ls -l /www/data/inflow/pipeline/03_display/   # 云端目标目录存在？
# 本地测试 SFTP 手动传
sftp inFlow_worker@<IP> <<'EOF'
  put /tmp/test.txt /www/data/inflow/pipeline/03_display/test.txt.tmp
  exit
EOF
```

- 连不上 → 公钥授权/`authorized_keys` 权限（700/600）；
- 权限拒绝 → `chown inFlow_worker:inFlow_worker /www/data/inflow/pipeline`；
- 修好之后：把 job `error_stage` 清掉、从 `composing` 重试（前端重跑或 `resume_for_retry(composing)`）。



### F5：心跳/租约相关（多 worker 或重启）

- 双 worker 并发不重复处理：靠 `FOR UPDATE SKIP LOCKED` + `claimed_at`，已内置；
- `kill` worker 后重启：`reclaim_own_host` 按 hostname 前缀回收本机遗留租约，无需手工清；
- 看到「已非本机租约，停止心跳」是**正常日志**，说明该 job 被别的 worker 接管。



### F6：云端重启 backend 后外部 job 丢失？

不会。`recover_captured_jobs` 已排除 `external_processing=true`，云端重启不碰外部 job；本地 worker 靠租约继续。

## 6. 回滚方案



### 6.1 停用分流（最轻量）

```bash
cd /www/wwwroot/<站点>
sed -i 's|^EXTERNAL_PROCESSING=.*|EXTERNAL_PROCESSING=false|' .env
./deploy/cloud/start-server.sh --restart --verify
./deploy/worker/stop-worker.sh      # 本地停 worker
```

效果：云端回到自己处理 URL（注意 ASR 403 会复现）；已 `external_processing=true` 的历史 job 不会自动翻转，如需恢复：`UPDATE ingest_jobs SET external_processing=false WHERE external_processing=true AND status NOT IN ('ready','failed','cancelled');`（谨慎，确认后再执行）。

### 6.2 撤代码

```bash
git log --oneline -5
git checkout <上一提交> -- <受影响文件>
./deploy/cloud/start-server.sh --restart --verify
```

> 若涉及迁移回滚（018 的三列），新版本代码不再引用即可，列可保留（`ALTER TABLE ... DROP COLUMN` 建议在确认无 worker 后手动执行，非必须）。
